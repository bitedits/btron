Drivers: Hardware Abstraction, PCIe Device Tree & Console Preservation

Comprehensive C99 developer manual for the B-System hardware drivers subsystem: modern PCIe bus enumeration and Flattened Device Tree (FDT) discovery, paravirtualized VirtIO MMIO engines, retro and vintage console preservation targets (Sony PlayStation 2, Bare-Metal MIPS, Raspberry Pi 2/3/4/5, NEC PC-98), GPU display backends (Sony GS, Broadcom VC4/VC6, VESA LFB), and UNIX-spirited Null COM stream conduits.

NASA JPL Rule 3 & Zero-Mock Architecture
All driver implementations adhere strictly to NASA JPL Rule 3 (zero dynamic heap allocation post-initialization) and Zero-Mock Discovery. Device probe routines directly interrogate CPU Model Specific Registers (MSRs), PCIe Enhanced Configuration Access Mechanisms (ECAM), Flattened Device Tree nodes, and physical MMIO controllers.

1. Hardware Abstraction Layer (HAL)

The B-System Driver subsystem decouples high-level Real-Body file operations, graphics rendering primitives, and text input front-ends from physical bus fabrics. Drivers expose uniform, non-blocking synchronous interfaces accessed via 32-bit device handles (ID):

2. PCIe Bus Architecture & Unified Device Tree (FDT)

To support modern multi-socket x86_64 servers, ARM64 workstations, and embedded system-on-chips (SoCs), B-System features a cleanroom PCIe Bus Enumeration pipeline and Flattened Device Tree (FDT) engine:

PCIe Host Configuration & Topology

  • Enhanced Configuration Access Mechanism (ECAM): Memory-mapped PCI configuration space mapped at standard physical aperture 0xE0000000 (or defined via ACPI MCFG table).
  • Bus-Device-Function (BDF) Scanning: Scans Buses 0..255, Devices 0..31, Functions 0..7. Identifies Vendor ID, Device ID, Subsystem ID, Class, and Subclass codes.
  • Base Address Registers (BARs): Automatically configures 32-bit and 64-bit non-prefetchable memory BARs and prefetchable memory apertures, mapping them into the kernel's virtual page tables.
  • MSI and MSI-X Vector Routing: Allocates dedicated message-signaled interrupt vectors, directly routing peripheral interrupts to specific target CPU cores without legacy PIC or IO-APIC line sharing.

Flattened Device Tree (FDT / DTB) Traversal

On ARM, RISC-V, and MIPS architectures where ACPI is absent, B-System parses the bootloader-provided Device Tree Blob (DTB):

  • Tokenizes FDT_BEGIN_NODE, FDT_PROP, and FDT_END_NODE structures in single-pass linear time with zero heap allocations.
  • Resolves compatible strings to match registered hardware drivers (e.g. "brcm,bcm2835-uart", "virtio,mmio", "raspberrypi,rp1").
  • Extracts reg properties to establish device base physical MMIO addresses and interrupts properties to attach T-Kernel 2.0 interrupt service routines.

4. Console Preservation Ports & Retro Hardware Drivers

B-System takes console and workstation preservation seriously. The system includes full bare-metal silicon drivers for iconic historical machines, providing authentic BTRON 3.20 desktop experiences on bare silicon:

4.1 Sony PlayStation 2 (Emotion Engine R5900)

Ported to the Sony PlayStation 2 (Emotion Engine MIPS-III R5900 64-bit CPU @ 294.912 MHz with 32 MB RDRAM):

  • Graphics Synthesizer (GS): Directly controls 4 MB of ultra-high-bandwidth embedded DRAM (eDRAM). Utilizes the Host-to-Local GIF DMA blitter (Channel 2) to transfer linear 32-bpp framebuffers from uncached KSEG1 RDRAM into GS pages, providing verified NTSC 640x448 and VESA 800x600 32-bpp progressive scan.
  • Cursor Preservation: Employs a non-destructive cursor backing buffer (cursor_saved[16 * 16]), restoring underlying pixels with zero trailing artifacts or screen smearing.
  • SIO0 Serial Console: Direct MMIO driver for the EE internal UART (0x1000F180), providing an interactive debug shell and logging channel.
  • DualShock 2 Pad: Full analog thumbstick and button integration over SIO2 (see §5).
  • USB Host (OHCI): Direct driver for the integrated Open Host Controller Interface at 0xBF801600, powering standard USB keyboards and mice.

4.2 Bare-Metal MIPS (QEMU Malta & Magnum)

Targeted at classic MIPS-III and MIPS64 workstation platforms:

  • NS16550 Serial Console: Standard COM1 UART driver at physical address 0x180003F8 (115200 baud, 8 data bits, no parity, 1 stop bit).
  • CP0 Timer & Interrupts: Direct programming of MIPS Coprocessor 0 Count and Compare registers to drive T-Kernel 2.0 system ticks and preemptive task scheduling.

4.3 Raspberry Pi Family (Pi 2B, 3B, 4B & 5)

Broadcom and RP1 bare-metal drivers spanning ARMv7 32-bit and ARMv8 AArch64:

  • Raspberry Pi 2B (BCM2836) & 3B (BCM2837): PL011 UART console, ARM local timer, VideoCore Mailbox Channel 8 framebuffer configuration, and SMSC9118 Ethernet.
  • Raspberry Pi 4B (BCM2711): VideoCore VI GPU, GIC-400 interrupt controller, Gigabit Ethernet (GENET), and DWC2 USB.
  • Raspberry Pi 5 (BCM2712 / RP1): Southbridge PCIe bridge enumeration, RP1 I/O controller, modern xHCI USB host, and VideoCore VII display scanout.

4.4 NEC PC-9801 / PC-9821

Supports legendary Japanese personal computers via cleanroom i386 real-mode bootstrap and 32-bit protected mode execution:

  • Planar VRAM Display: Drives 4-plane 16-color interleaved graphics memory (0xA8000..0xB8000) with hardware plane masking.
  • A20 Gate Control: Directly drives PC-98 system port 0xF2 for high-memory access.
  • Peripherals: 8251 USART serial communications, INT 1Ah real-time clock, and PC-98 keyboard matrix decoding.

6. Display Architecture & GPU Acceleration Engines

The display driver pipeline abstracts varied graphics hardware into a unified GDEV rendering surface for Display Primitives (DP):

  • Sony Graphics Synthesizer (GS): 4 MB ultra-fast eDRAM. Bypasses sub-pixel rasterizer limitations using the hardware Host-to-Local Blitter to stream linear RDRAM into swizzled eDRAM pages with zero CPU overhead.
  • Broadcom VideoCore IV / VI (VC4 / VC6): Interrogates the VideoCore GPU via Mailbox Channel 8 property tags to establish pixel format (ARGB8888), double-buffered scanout pitch, and hardware cursor overlays.
  • VESA Linear Framebuffer (LFB): Universal 32-bpp linear memory buffer established by UEFI GOP or BIOS INT 10h VBE extensions on modern x86_64 PCs.
  • VirtIO GPU: Paravirtualized 2D host-accelerated scanout with resource transfers and display flushes.

7. Serial Communications & Null COM Conduits

B-System unifies traditional physical serial communication with the classic UNIX spirit of virtual conduits, reimagined with authentic BTRON non-blocking event semantics:

Physical Serial Drivers

Supports National Semiconductor NS16550, ARM PL011, PlayStation 2 SIO0, and NEC 8251 USART under standard naming (com1, com2, sio0, uart0).

Virtual Null COM Ports (The BTRON Pipeline)

Registered as null0, null1, vcom0, and vcom1, these virtual drivers provide high-speed, non-blocking inter-process and testing conduits:

  • Sink Mode (/dev/null Semantics): When opened independently, writes to null0 discard bytes immediately and return success (E_OK), while reads return 0 bytes (end-of-stream).
  • Paired Loopback Conduit (Cross-Talk PTY): When both ends of a pair are opened (e.g. null0 $\leftrightarrow$ null1), data written to one side is immediately enqueued into a bounded static circular ringbuffer and wakes the reader on the opposite side via T-Kernel 2.0 message buffers (tk_snd_mbf) and delivers an EV_DEV_READY event.
  • Deterministic Testing: Allows the B-System shell (clu) and terminal emulator (gterm) to be driven programmatically in automated continuous integration tests without physical serial cabling or pseudo-terminal kernel leaks.

8. Data Structures & Descriptors

Device Management Descriptor (DEV_DESC)

typedef struct {
    ID    dev_id;       /* Unique 32-bit device identifier */
    UW    type;         /* Device class: DEV_BLOCK, DEV_CHAR, DEV_NET, DEV_GPU */
    char  name[32];     /* Hardware device label (e.g. "vda", "com1", "gs0") */
    UW    flags;        /* DEV_READONLY, DEV_DMA_CAPABLE, DEV_ACTIVE */
    UW    block_size;   /* Native block transfer granularity (512, 1024, 4096) */
    UD    total_blocks; /* Total sector or byte capacity */
} DEV_DESC;

PCIe Device Address Descriptor (DEV_PCI_ADDR)

typedef struct {
    UB    bus;          /* PCI Bus (0..255) */
    UB    device;       /* PCI Device (0..31) */
    UB    function;     /* PCI Function (0..7) */
    UH    vendor_id;    /* PCI Vendor ID (e.g. 0x1AF4 for VirtIO) */
    UH    device_id;    /* PCI Device ID */
    UW    bar_phys[6];  /* Physical base addresses of BAR0..BAR5 */
    UW    bar_size[6];  /* Memory mapped sizes of BAR0..BAR5 */
    UB    irq_line;     /* Allocated interrupt vector or MSI index */
} DEV_PCI_ADDR;

9. Device Driver C99 API Reference

opn_dev ID

Opens a registered hardware device, virtual conduit, or paravirtualized bus interface by name.

ID opn_dev(const char *dev_name, UW mode);
rea_dev ER

Reads sectors, raw byte streams, or input event packets from the target device into a kernel or user buffer.

ER rea_dev(ID dev_id, UD start_block, void *buf, UW count);
wri_dev ER

Writes data blocks or character streams to the device, flushing write-back caches and signaling receiver tasks.

ER wri_dev(ID dev_id, UD start_block, const void *buf, UW count);
ctl_dev ER

Executes an architecture-specific control command (IOCTL), such as changing UART baud rate, setting GPU resolution, or querying PCIe BAR addresses.

ER ctl_dev(ID dev_id, UW cmd, void *arg, UW arg_sz);
dev_tree_find ER

Queries the active Flattened Device Tree (FDT) or PCIe topology for a node matching a given compatibility string or hardware path.

ER dev_tree_find(const char *compatible, DEV_DESC *out_desc);

10. Canonical Implementation Examples

Inter-Task Communication via Null COM Conduits

The following example demonstrates opening a paired virtual Null COM port conduit (null0 and null1) to stream diagnostic commands between tasks: 

#include <btron/device.h>
#include <btron/error.h>

void test_null_com_conduit(void) {
    /* 1. Open primary and secondary ends of the virtual conduit */
    ID tx_port = opn_dev("null0", 0);
    ID rx_port = opn_dev("null1", 0);
    if (tx_port < 0 || rx_port < 0) return;

    /* 2. Write command string into transmit end */
    const char msg[] = "CLU_TEST_PING\n";
    wri_dev(tx_port, 0, msg, sizeof(msg));

    /* 3. Read streamed command on receive end */
    char recv_buf[32];
    ER er = rea_dev(rx_port, 0, recv_buf, sizeof(recv_buf));
    if (er == E_OK) {
        /* Packet verified via zero-allocation ringbuffer */
    }

    /* 4. Release device ports */
    cls_dev(tx_port);
    cls_dev(rx_port);
}
