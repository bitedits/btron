File System: B-FS, Chokanji & Volume Architecture

Comprehensive C99 technical specification and system programming reference for the B-System volume layer: multi-format support spanning vintage Chokanji (B-right/V 4.02), B-FS V1 block allocation, modern B-FS V2 write-ahead redo journaling (WAL), and the four standard system volumes (/SYS, /ANDERS, /CHOKANJI, /NEW-V2).

Architectural Scope & Tenets
The BTRON File System departs fundamentally from UNIX linear byte streams. A BTRON file is an ordered collection of typed Real-Body records (RT_LINK, RT_TADDATA, RT_PROG, RT_VECTOR). Adhering to NASA JPL Rule 3, the storage subsystem operates without post-boot dynamic heap allocation, providing deterministic I/O across bare-metal workstations, embedded microcontrollers, POSIX emulators, and paravirtualized cloud hypervisors.

2.1 Chokanji (B-right/V 4.02 Filesystem)

The Chokanji filesystem format (represented by FS_TYPE_BRIGHTV, code 0x6402) originates from Personal Media Corporation's commercial B-right/V operating system for x86 PCs. While standard TRON specification documents specify big-endian fields, PMC adapted the on-disk structures to little-endian byte ordering (magic 0x52FE) for native performance on Intel 80386/80486 processors.

  • Block Organization: 1024-byte logical blocks. Block 0 contains the 128-byte System Header.
  • FID Table: Indexed 4-byte entries. The high 3 bytes define the logical block address of the file's header block; the lower 1 byte stores the reference link count (1 to 255). FID 0 is reserved for the root folder.
  • Short-Name Hash Table: A 4-byte hash per FID that accelerates file path lookups. File names are packed into ten 32-bit words (up to 40 UTF-8 / TRON-Code bytes) and hashed via sequential XOR and 1-bit right rotation: 
    hash = 0;
for (int i = 0; i < 10; i++) {
    hash ^= NAME[i];
    hash = (hash >> 1) | (hash << 31); /* Rotate Right 1 bit */
}
  • Allocation Bitmaps: Dual bitmaps—a Used-Block Bitmap (0 = free, 1 = allocated) and a Bad-Block Bitmap for defective media tracking.
  • Interoperability: B-System mounts raw PMC hard disk images and QEMU copy-on-write files (hda.qcow2) transparently into the unified VFS at /CHOKANJI.

2.2 B-FS V1 (Standard FAT-like Block Filesystem)

B-FS V1 (FS_TYPE_STD, code 0x6400) is the reference cleanroom implementation of the canonical BTRON3 3.20 specification. It functions as a lightweight, highly deterministic block filesystem with architectural simplicity comparable to MS-DOS FAT, but enriched with typed Real-Body metadata and extent fragment tables:

  • Endianness: Big-endian (VOL_MAGIC_BE = 0x42FE).
  • Deterministic Block Allocation: Operates on flat 1024-byte logical blocks. A single allocation bitmap maps all blocks, eliminating non-deterministic tree balancing overhead during embedded writes.
  • File Header (192 bytes): Every Real Body begins with a 192-byte header block defining permissions (FFLG_PERM, FFLG_WPROTECT, FFLG_READ, FFLG_WRITE, FFLG_EXEC), modification timestamps, 40-byte UTF-8 file name, and an extent table: 
    typedef struct __attribute__((packed)) {
    UW   start_blk;   /* Starting logical block address */
    UH   num_blks;    /* Number of contiguous blocks     */
} FragEntry;          /* Max 32 fragments per Real Body */
  • Level 0 Record Index: Following the 192-byte FileHeader within block 0 of the file, up to 40 RecordIndex entries (16 bytes each) index the ordered Real-Body records. Files exceeding 40 records allocate indirect index blocks.
  • Suitability: Ideal for microcontroller flash memory, RAM disks, boot ROMs, and real-time sensor logging where execution time bounds must be mathematically proven.

2.3 B-FS V2 (Modern Redo-Journaled BeFS Engine)

B-FS V2 (FS_TYPE_MODERN, code 0x6403) combines the high-performance metadata capabilities of Haiku's BeFS with BTRON's native record model and modern artificial intelligence workloads:

Dual-Anchor Superblock Architecture
To guarantee 100% backward compatibility with legacy BTRON boot ROMs while providing full 64-bit capability, B-FS V2 implements a Dual-Anchor Superblock:
  • Block 0 (128 bytes): VolumeHeaderV2 (Magic 0x62FE). Classic bootloaders read this block to determine basic volume geometry, root FID, and feature flags without faulting.
  • Block 1 (512 bytes): bfs_super_block_v2 (Magic 'BFS1' / 0x42465331). Modern B-System kernels read this block to activate 64-bit Allocation Groups, journal bounds, and B+Tree roots.

Key Technical Innovations in B-FS V2:

  • 64-bit Block Runs & FIDs: 
    typedef struct __attribute__((packed)) {
    int64_t  allocation_group; /* 48-bit AG index */
    uint16_t start;            /* 16-bit block offset in AG */
    uint16_t length;           /* Contiguous block count */
} block_run_64;
typedef uint64_t fid64_t;     /* (AG << 16) | start */
  • Write-Ahead Redo Journaling (WAL): All metadata modifications (inode updates, B+Tree balancing, block allocations) are written sequentially to a circular journal buffer (log_blocks) before touching on-disk structures. On reboot after power failure, the journal replayer scans between log_start and log_end, restoring disk consistency in milliseconds without full-volume scans.
  • 512-Byte Inode with Inline Small Data: Every file inode (bfs_inode_v2) contains 12 direct block runs, 1 indirect run, 1 double-indirect run, and an inline small_data region. Small records (such as TAD text clips or vector embeddings) are embedded directly within the inode sector, requiring zero additional disk reads.
  • Parameterized B+Tree Engine: Supports selectable node page sizes (1024, 2048, 4096, 8192 bytes) with B-Link concurrency control for million-record directories and fast attribute indexes.
  • Native Vector Storage (RT_VECTOR): Dedicated support for dense floating-point embedding vectors, enabling nearest-neighbor (ANN) similarity queries across TAD documents directly at the filesystem layer.

4. Real-Body & Record Architecture

In BTRON, a file is structured as a typed sequence of records rather than an unformatted byte stream. Each record is identified by a 16-bit type tag:

│   │ Record 1 (RT_LINK)     │ Virtual Object Fusen Link Descriptor  │   │
│   ├────────────────────────┼───────────────────────────────────────┤   │
│   │ Record 2 (RT_TADDATA)  │ TAD Segment: Formatted Multilingual   │   │
│   ├────────────────────────┼───────────────────────────────────────┤   │

│   ├────────────────────────┼───────────────────────────────────────┤   │
│   │ Record 4 (RT_PROG)     │ Executable Machine Code / Bytecode    │   │

Record Type Value Payload Structure Semantic Description
RT_LINK 0x0001 FS_LINK (Target FID + Attributes) Virtual Object (Fusen) link pointing to another Real Body.
RT_TADDATA 0x0002 Binary TRON Application Databus (TAD) Rich multilingual text, geometric shapes, fonts, and inline Fusen.

5. File System C99 API Reference

vol_mount Volume *

Probes a block device, detects its filesystem generation (Chokanji, B-FS V1, or B-FS V2), validates superblocks, and attaches it into the active volume registry.

Volume *vol_mount(BlkDev *dev);
vol_format int

Formats a block device with a clean standard B-FS V1 volume, writing system headers, initial allocation bitmaps, root FID 0, and short-name tables.

int vol_format(BlkDev *dev, UW nfmax, UW nlb, const char *name);
vol_format_v2 int

Formats a block device with a high-performance modern B-FS V2 journaled filesystem, configuring dual-anchor superblocks, allocation groups, journal size, and vector indexes.

int vol_format_v2(BlkDev *dev, UW nfmax, UW nlb, const char *name, UW block_size, UW btree_size, UW journal_blocks, UW features);
opn_fil FID

Resolves a path across mounted volumes (e.g. /SYS/FONTS/KANJI16 or /ANDERS/PROJECT.TAD) and returns an active File ID handle.

FID opn_fil(const char *path, UW mode);
rea_rec ER

Reads an ordered typed record from an open Real Body into a user-provided buffer.

ER rea_rec(FID fid, UH rec_type, UW rec_idx, void *buf, UW buf_sz, UW *out_actual);
wri_rec ER

Appends or overwrites a typed record within a Real Body, updating index blocks and committing journal transactions.

ER wri_rec(FID fid, UH rec_type, UW rec_idx, const void *data, UW data_sz);

6. Canonical Implementation Examples

Mounting Volumes and Reading TAD Records

The following example illustrates mounting the user workspace volume /ANDERS, opening a document, and streaming its TAD payload: 

#include <btron/fs/vol_api.h>
#include <btron/file.h>
#include <btron/fs/fs_types.h>

void inspect_user_document(void) {
    /* 1. Open backing storage file for user volume */
    BlkDev *dev = blk_file_create("btron_anders.vol", 0, 0);
    if (!dev) return;

    /* 2. Mount volume into B-System VFS */
    Volume *v = vol_mount(dev);
    if (!v) {
        blk_destroy(dev);
        return;
    }

    /* 3. Open Real Body by path */
    FID fid = opn_fil("/ANDERS/NOTES.TAD", FFLG_READ);
    if (fid != FID_INVALID) {
        UB buffer[1024];
        UW actual = 0;

        /* 4. Read primary TAD record (RT_TADDATA) */
        ER err = rea_rec(fid, RT_TADDATA, 0, buffer, sizeof(buffer), &actual);
        if (err == E_OK) {
            /* Process TAD text and graphic segments */
        }
        cls_fil(fid);
    }

    /* 5. Unmount volume when shutting down */
    vol_umount(v);
}
