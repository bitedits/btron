B-Book / B-MSX

tronMSX — B-MSX: The MSX2+ Home of the B-System

B-MSX specifies the MSX2+ home of the B-System: an MSX program is a first-class real-body and the embedded core tronMSX boots it in a native BTRON window. The book contains the machine model (Part 1), the silicon contracts (Part 2), the BIOS and boot trace (Part 3), the BMSX record and launch algorithm (Part 4), the core API and threading contract (Part 5), the media integration contracts (Part 6), the toolchainMSX kit (Part 7), the frame-granular time-travel debugger (Part 8) and the acceptance vectors (Part 9). openMSX and blueMSX are transition instruments for existing users; B-MSX is the destination. Every constant, byte offset, signature, error code and acceptance measurement needed to implement the first core, the debugger and their tests is stated in this book.

0. Scope & Normative Rules

B-MSX specifies the B-System's MSX2+ home: a cross-dev kit plus the embedded core tronMSX. It is not a BTRON 3.20 port to the MSX machine. Current B-System is a C99 clean-room of BTRON3 3.20 aimed at ARM64, x86_64 UEFI, PS2 MIPS, PC-98, 68000 and POSIX; MSX is a banked Z80 (or R800) machine with a 64 KiB address space and a VDP. This book defines the subset that hosts it: real and virtual body records, a bounded emulator core, and TAD-renderable documentation.

C++ MUST NOT appear inside the BTRON boundary. Everything this book builds — tronMSX, tronmsx_tt, msxpak, mssym and the test harness — is C99 and MUST link with zero C++ translation units and zero runtime heap. Host tools outside the boundary (the toolchainMSX assembler, compiler and linker, and the reference emulators) keep their own languages. The boundary is enforced by the acceptance vectors AV-8 and AV-11.

Normative vocabulary: MUST and MUST NOT mark hard requirements — a build that violates one fails acceptance. SHOULD marks a default that may be varied with a written justification. MAY marks optional behaviour.

Every numeric constant in this book carries one of the three basis labels below, in the table row or sentence that defines it. No other qualification of a number appears in the text.

Primary RAM is one 64 KiB pool, presented as the page 2 and page 3 views, so the machine value in a BMSX record and the size field of the checkpoint header (8.2) always describe the same pool. A 128 KiB machine value MUST be accepted and run as 64 KiB, with MSX_ERR_RAM reported as an advisory window rather than as a hard failure: no first-core program addresses more than 64 KiB.

  • Pool addressing: a store to page 2 or page 3 MUST land at (page == 2 ? off : 0x4000 + off) inside the 64 KiB pool.
  • View and pool are distinct: selecting the cartridge slot for page 2 with 0xF8 bits 4–5 makes the page 2 view ROM block 1 of a 32 KiB cartridge, while the pool keeps all 64 KiB of RAM addressable and page 3 remains RAM in every combination. Without that select, page 2 is EXRAM low.
  • ROM regions are read-only at the bus level: a Z80 write to a page currently mapped as ROM MUST be discarded, never faulted.

1.3 Slot System & I/O Port Map

Port 0xF8 selects the primary slot per page: bits 0–1 select page 0, bits 2–3 page 1, bits 4–5 page 2, bits 6–7 page 3. Ports 0xF9–0xFC select the secondary slot for pages 1–3 respectively, and take effect only where the primary slot of that page is 0. Port 0xF7 selects the upper-64 KiB EXRAM page (0–3) on a 128 KiB machine; the first core pins it to 0. The first core powers up with page 0 on primary slot 0 (BIOS), page 1 on the cartridge and pages 2–3 on EXRAM; a stored page-2 select of slot 1 re-points the page 2 view at cartridge ROM block 1, as 1.2 requires, and any other stored value keeps EXRAM. The core MUST accept and store writes to 0xF8–0xFC: C-BIOS and games poke these ports, and a dropped store breaks the C-BIOS boot trace.

Part 2 — Silicon Contracts

2.1 Z80 Core & Interrupts

The CPU MUST be a cycle-accurate-at-instruction-boundary Z80 core (superzazu/z80 shape — instruction cycles, not per-T-state interleaving; 7.7). Required semantics, each of which is an acceptance-testable claim:

  • DI/EI delay: an interrupt MUST NOT be accepted by the instruction that executes DI or EI; acceptance resumes at the next instruction boundary.
  • IM 0 / IM 1 / IM 2: MSX uses IM 2 for the VDP IRQ. The IM 2 vector is (I << 8) | 0xFF, and the acknowledge cycle MUST cost 280 T in total with the standard prologue.
  • NMI: edge-triggered. The periodic 1.34 ms generator raises it, and reading VDP status at 0x88 inside the handler clears the source. NMI entry costs 256 T.
  • HALT: the core MUST consume idle T in the T_PER_FRAME/6 pattern while halted — 100 T per iteration is the accepted emulator convention — and MUST still service interrupts; a busy-spin substitute fails BIOS timing tests.
  • I/O timing: every IN and OUT MUST take at least 4 T, and the device MUST observe the transfer at the end of the instruction. No port MAY be modelled as zero-latency memory.

Cycle costs for the instructions the boot trace uses, from the Z80 documentation (Hardware): NOP 4 T · LD A,(nn) 13 T · LD HL,(nn) 16 T · JP (HL) 5 T · CALL nn 17 T · CALSLT prefix sequence DI/POP×6/EI/JP 53 T plus the callee · RET 10 T · IM 2 8 T · OUT (n),A 11 T · IN A,(n) 11 T · HALT 4 T per exit.

The SCREEN 2 colour law Hardware is the one that is easy to get wrong, so it is stated normatively here: Graphics 2 has a 6 KiB colour table, not a 768-byte one, and the colour byte lives at the same address inside it as the pattern byte does inside the 6 KiB pattern table — index = 8*code + y%8 with code = name + 256*(y/64). Reading the colour at CT + code, as the Graphics 1 law would suggest, collapses every eight pattern rows onto one CR byte and makes a SCREEN 2 game that paints per-row ink/paper pairs (Lode Runner is the reference case) render almost entirely black. Graphics 1 keeps the 768-byte table with name >> 3; the two laws are NOT interchangeable.

Palette: sixteen 16-bit colour registers in VRAM, written through auto-increment as RRRRGGGG GGBBBB00, low byte then high byte. The RGB565 conversion law is duplication: each 4-bit channel c maps to 5 or 6 bits as R5 = c>>1, G6 = c<<2 | c>>2, B5 = c>>1. The palette table MUST be a single static array; runtime writes overlay it and reset restores it.

2.5 PPI, Keyboard Matrix, Joystick

8255 PPI at 0x10–0x13 and 0xA8–0xAB, with the roles the MSX standard gives its ports: port A (0xA8) is the primary slot-select latch — write it and the page map changes, read it and the latch comes back; port B (0xA9) is the keyboard column data for the row currently selected, active low; port C (0xAA) holds the keyboard row select in its low nibble and the cassette lines in its high one; 0xAB is the mode-set word, and a value with bit 7 clear is an 8255 bit-set/reset command against port C. C-BIOS writes 0x82 there at start-up. The joystick pins are not on the PPI: they are read on the PSG ports, 2.5's joystick table.

Keyboard: the row select is the low nibble written to port C at 0xAA, so sixteen row addresses exist, and the eight column bits are read back active-low from port B at 0xA9. C-BIOS' own scan does exactly this and nothing else: over a 500-frame boot the tracer records 230 selects apiece for rows 0 through 9 at 0xAA, and 230 reads apiece at 0xA9 from PC=177F. The matrix is therefore the ten rows the BIOS strobes, each of eight column bits — 80 cells, with rows 10 through 15 reading all-released because no key is wired to them. The "8 rows × 10 columns" of earlier drafts counted those same 80 cells the other way round and is retired here; the core MUST present them through the setter msx_kbd_down(row, col) used by the window event layer, with row the value written to 0xAA.   1. msx_reset establishes the machine's reset state: PC = 0x0000, SP = 0xFFFC, AF = BC = DE = HL = IX = IY = 0xFFFF, I = 0xFF, R = 0, IM = 0, IFF1 = IFF2 = 0, not halted, every slot and port latch at its idle value, and RAM initialized to 0x00 per D3 of 8.1. The Z80 leaves these registers undefined on hardware, so this list is Normative: it is the emulator reset convention, and the golden checkpoints of 8.2 pin it.
  2. C-BIOS initializes the VDP registers, selects SCREEN 0 and clears VRAM.
  3. C-BIOS scans the cartridge pages for the AB signature at 0x4000 and validates the header table above. A 32 KiB ROM takes the INIT80 path with block 1 reached through the page 2 select of 1.2.
  4. C-BIOS calls INIT80, then INIT19 and SHELL at their header addresses. The cartridge's INIT80 return value decides whether the cartridge keeps control, the search continues in the next slot, or BASIC runs; an ASCII-only statement is skipped per the version byte.
  5. With the cartridge in control, the game loop runs against the VDP and PSG contracts of Part 2. With no cartridge, the window presents the C-BIOS BASIC banner.

A cartridge installs its NMI and keyboard hooks through the BIOS, which keeps the hook addresses in its own system variables and calls them from its NMI and keyboard chains. The core supplies the NMI edge and executes whatever address that chain reaches; it MUST NOT call cartridge code directly.

4.2 Launch Algorithm

Opening the virtual-body creates one BTRON window and starts the machine. No separate emulator process, no “pick a file” step. Normative sequence:

  1. Read + validate the BMSX record (4.1 law). Fail ⇒ error window, never a silent hang.
  2. Resolve settings: bios.msx2p, bios.msx2pext, bios.disk, bios.kanji, machine (default MSX2+). Record's bios_key overrides the default key name (not its value). Missing BIOS ⇒ window naming the key.
  3. Create the BTRON window: title = name, client area 512×424 (MSX2+ ×2) or 256×212 (×1), WND_ATTR_TITLE | WND_ATTR_BORDER | WND_ATTR_SLIDING_TAB. The menu bar carries reset, pause, disk slot and quit as BTRON menu parts (window), and the debugger opens its own windows as specified in 8.4.1.
  4. Build the machine: Z80 at Z80_HZ, 64 KiB RAM, V9958, PSG, PPI; map BIOS into page 0; insert the program per kind — rom to page 1, com to drive A when the disk step lands. The first core accepts rom only and returns MSX_ERR_KIND for 2, 3 and 4 with the record's name in the message.
  5. Reset and run. The first presented frame follows the BIOS handoff (INIT80 trace, 3.2). The window MUST NOT show a firmware menu unless flags bit 0 (pause at first frame) is set.

Input travels through the slot, not through the ring: an 8-byte command entry cannot carry an 80-bit matrix. KBD_SYNC is the per-step tick marker whose a0 is the slot's sequence number, and the matrix itself is the one published snapshot (the ten row bytes of 2.5, one byte per strobe row, plus joystick). The channel is level-driven and single-slot, so a dropped tick cannot desynchronize state: the next step reads the newer matrix, and the input log records the matrix the machine saw (8.2).

The MSX_CORE loop paces itself on msx_run_frame wall time against 16.67 ms. It MAY skip the presentation of a frame. toolchainMSX is the shipped Z80 build kit: rasm as the assembler, z88dk (zcc, z80asm, appmake) as the compiler driver, linker and packager, and msxpak as the thin C99 real-body wrapper. C++ stays prohibited inside the BTRON boundary (Part 0): tronMSX, msxpak and the harness are C99 with zero runtime heap, and Z80-side C is C99 (front-end rule below).

This Part supersedes the design note's Pasmo-only policy on three architectural grounds:

  • License. Pasmo is GPL; Rasm is MIT and z88dk is Clarified Artistic. The kit vendors into the B-System tree with no copyleft exposure, and Rasm is C, so it sits inside the boundary.
  • Linking. Pasmo emits no relocatable objects, which limits a build to one ORG, one invocation and one target. z80asm links sections and libraries, so multi-file C plus assembly, sections, and library code are produced by the linker; appmake emits the emulator artifacts (.cas, .dsk carrying a .com, ROM image) that 7.5 requires.
  • Debug surface. Rasm exports symbol and breakpoint files plus makefile dependencies. The symbol file is the input the openMSX Symbol Manager reads and the input the time-travel debugger consumes (Part 8): one symbol artifact serves both tools.

The one thing z88dk must not be allowed to keep is its own C startup. z88dk's +msx target is the classic library and its BIOS-shaped CRT owns the first bytes, which collides with the BMSX contract in Parts 3 and 4. Normative resolution: toolchainMSX ships its own startup, toolchainMSX/crt0_btron.asm in Rasm syntax, written into the cartridge header at 0x4000, linked with -crt0=crt0_btron.asm and built -Ostandard (never -Omax), so the CRT obeys the boot trace of 3.2. Front-end rule: C99 conformance comes from -compiler=sdcc -clib=sdcc_iy; sccz80 (near-C90) is not approved for new C sources. Library rule: the classic library supplies I/O and memory-move helpers over the fixed 16-byte-pointer BIOS conventions only. A BMSX program MUST NOT link the classic library's malloc (AV-11 asserts the absence of the symbol). A program that wants a heap declares a static pool: bounded, inside its own .DATA/.BSS. The BMSX record (4.1) carries no heap field and MUST NOT gain one. Inline BIOS calls stay in Rasm assembly.

Part 8 — Time-Travel Debugger

B-MSX ships a frame-granular time-travel debugger: step backwards frame by frame, jump to any frame inside the rewind window, stop on a PC breakpoint or a page watchpoint, and read the Z80, VDP and PSG state at the historical instant. It runs on the same machine instance as the emulator, in its own top-level BTRON windows (8.4.1), opened from the same real-body. Reverse execution is a consequence of the machine model of Part 2 and the determinism law below, not a layer added on top of it. Everything in this Part is normative for the debug shape; 8.5 states what the shipping shape excludes.

8.1 The Determinism Law (D1 … D7)

The equation the debugger stands on:

state(N+1) = step( state(N), input(N) )

  input  == the published snapshot in the input slot (5.2), logged as 16 B per step (8.2)

8.2 Input Log, Checkpoints and the Replay Algorithm

Two static structures make the law rewinding. The input log records the machine's entire host-visible history in 16 bytes per frame; the checkpoint ring stores full machine snapshots, so rewind is a restore and not a re-simulation from power-on. 

typedef struct {            /* one record per EXECUTED step (not per presented frame) */
    uint8_t  kbd[10];       /* the whole 10x8 matrix as the step sees it (2.5), 80 bits */
    uint8_t  joy;           /* TRGA / TRGB / steering bits, level snapshot (2.5) */
    uint8_t  cmd;           /* cmd_ring byte consumed this step: RESET|PAUSE|RESUME|QUIT|none */
    uint8_t  drops;         /* bit0 pcm drop, bit1 cmd drop — D5: host-timed events are data */
    uint8_t  pad[3];        /* zero; keeps the record 16 B and the row math a shift */

Restore and replay, in order:

  1. Pick the newest checkpoint K ≤ target; verify header magic, version, CRC32 and msx_body_hash() before touching the machine. A failed verify leaves the machine exactly as it was and returns MSX_ERR_TT_STALE; a target older than the ring head returns MSX_ERR_TT_RANGE. A partial application is not a permitted outcome.
  2. Copy the 65,536-byte and 131,072-byte blocks back, then the 256-byte header fields into their live variables. This runs on MSX_CORE at a frame boundary, the pause rule of 8.3.
  3. Flush pcm_ring and reset the PSG phase accumulators to the restored values, so no sound from the discarded future plays and the next frame's PCM is the historical one.
  4. Replay forward from K to the target: for each frame feed tt_input_log[frame] into the machine and run exactly one msx_run_frame-equivalent step, headless: no blit, no PCM submit, no pacing sleep.
  5. Render once from the restored VRAM to present the target frame. Rendering is derived from VRAM state and not from CPU execution, so a single-frame TT_STEP back needs no replay; that is the 8 ms budget of 8.5.
