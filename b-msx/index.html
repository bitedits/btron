B-Book / B-MSX

tronMSX — B-MSX: The MSX2+ Home of the B-System

The complete, self-describing specification of B-MSX: the MSX2+ home where an MSX program is a first-class real-body and the embedded core tronMSX boots it in a native BTRON window. C99-only silicon (Z80 at 3.58 MHz, V9958, AY-3-8910, slot system), the BMSX record at byte offset, the launch algorithm and its error codes, the core API and threading contract, and the integration seams into B-Audio, B-Sound, B-Video and B-Media; the toolchainMSX kit (Rasm + z88dk) and the frame-granular time-travel debugger that the core's determinism law makes possible. openMSX and blueMSX are transition instruments for existing users, not the destination. A developer who reads only this book can implement the first core, the debugger and their acceptance tests.

0. Scope & Normative Rules

B-MSX specifies the B-System's MSX2+ home: a cross-dev kit plus the embedded core tronMSX — not a full BTRON 3.20 port to the machine. Current B-System is a C99 clean-room of BTRON3 3.20 aimed at ARM64, x86_64 UEFI, PS2 MIPS, PC-98, 68000, and POSIX; MSX is a banked Z80 (or R800) machine with a 64 KiB address space and a VDP. This book defines the teaching subset that can host it: real/virtual body records, a bounded emulator core, and TAD-renderable documentation.

C++ is prohibited inside the BTRON boundary — this is a B-System language law, not a style preference. Everything this book builds (tronMSX, tronmsx_tt, msxpak, the test harness) is C99 and MUST link with zero C++ translation units and zero runtime heap. External host tools that merely sit outside the boundary (the toolchainMSX assembler, compiler and linker, the reference emulators) keep their own languages; the boundary is what the acceptance tests enforce (AV-8 host core, AV-11 program and build-shape hygiene).

Normative vocabulary: MUST / MUST NOT are hard requirements — a build that violates them fails acceptance; SHOULD is a default that may be varied with a written justification; MAY is optional. Every numeric constant in this book is either proven (fixed by the MSX standard or a chip manual and testable) or inferred (a first-core choice that may be calibrated); inferred constants are labelled explicitly. Nothing here requires reading doc/md/MSX.md first; the design note is the origin, this book is the specification.

First core scope (fixed): MSX2, 64 KiB main RAM, one 32 KiB cartridge, SCREEN 0–5 rendering, PSG audio, keyboard matrix, C-BIOS fallback. Explicitly out of the first core: disk drive, Kanji ROM, FM (YM2413/OPLL), R800, MegaROM mappers beyond a single 32 KiB page pair, SCC, MIDI. Each of those is a later step with its own acceptance delta; adding one MUST NOT change any constant marked proven.

The time-travel debugger is a goal of B-MSX, not an exclusion (Part 8). It is affordable precisely because the core is small and deterministic: reverse execution here is a consequence of the machine model, not a feature bolted onto it. Two consequences bind the first core from its first commit, before any debugger exists: the determinism law (8.1) constrains msx_run_frame itself, and the per-frame input log (8.2) reuses the level-driven KBD_SYNC snapshot that 5.2 already requires. The debugger's own storage — the checkpoint ring — is compiled out of the shipping window build, so the 5.3 static bound is unchanged; it exists only in the make msx-tt harness (8.5).

Book status. B-MSX is spec-first: no src/emulators/msx/, no include/emulators/tronmsx.h and no include/emulators/tronmsx_tt.h exist in the tree yet. File names in Part 5 and Part 8 are the required shape of the module to implement, not shipped code. See Verification Status.

1.3 Slot System & I/O Port Map

Port 0xF8 selects the primary slot per page (2 bits each: bits 0-1 → page 0, 2-3 → page 1, 4-5 → page 2, 6-7 → page 3). 0xF9–0xFC select the secondary slot for pages 1–3 respectively, but only when the primary slot is 0 (the sub-slot machine). Port 0xF7 selects the upper-64 KiB EXRAM page (0-3) when a 128 KiB machine is configured — pinned to 0 in the first core. First core MUST implement: page 0 always primary slot 0 (BIOS), page 1 always the cartridge, pages 2–3 always EXRAM, and MUST still accept and store writes to 0xF8–0xFC (the BIOS and games poke them; ignoring the store, rather than ignoring the port, breaks C-BIOS boot).

Part 2 — Silicon Contracts

2.1 Z80 Core & Interrupts

The CPU MUST be a cycle-accurate-at-instruction-boundary Z80 core (superzazu/z80 shape — instruction cycles, not per-T-state interleaving; see 7.6). Required semantics, each of which is an acceptance-testable claim:

  • DI/EI delay: an interrupt MUST NOT be accepted by the instruction that executes DI or EI; acceptance resumes with the next instruction boundary.
  • IM 0 / IM 1 / IM 2: MSX uses IM 2 for the VDP IRQ. IM 2 vector = (I << 8) | 0xFF; acknowledge cycle cost MUST be 280 T total with the standard prologue.
  • NMI: edge-triggered; the periodic 1.34 ms generator raises it, and reading VDP status at 0x88 inside the handler clears the source. NMI entry cost 256 T.
  • HALT: the core MUST consume T_PER_FRAME/6-style idle T (100 T is the accepted emulator convention) while halted and still service interrupts — a busy-spin substitute fails BIOS timing tests.
  • I/O timing: every IN/OUT MUST take ≥ 4 T and the device MUST observe the transfer at the instruction end; no port may be modelled as zero-latency memory.

A representative cycle table for the instructions the boot trace uses (proven, from the Z80 manual): NOP 4T · LD A,(nn) 13T · LD HL,(nn) 16T · JP (HL) 5T · CALL nn 17T · CALSLT prefix sequence DI/POP×6/EI/JP ≈ 53T + callee · RET 10T · IM 2 8T · OUT (n),A 11T · IN A,(n) 11T · HALT 4T/exit.

Light pen MUST NOT be emulated beyond reporting FG1=0 always.

2.5 PPI, Keyboard Matrix, Joystick

8255 PPI at 0x10–0x13 (and 0xA8–0xAB): port A = joystick/pin input, port B = output (C-BIOS uses it for nothing audible), port C = cassette/mixed. Control word MUST be honoured to the extent that setting A/C to input returns all-1 when idle.

Keyboard: OUT 0xFE, row (row 0-7, bit 7 of low nibble ignored) then read 10 columns as active-low bits from PPI A (the 0xFE read or INROW path). The core MUST present the matrix as a 8×10 bit array with an msx_kbd_down(row, col) setter used by the window event layer; debouncing is the host UI's job, not the core's. Required first-core keys (proven matrix positions, row/col 0-based): SPACE 0/0, ENTER 0/1, STOP 0/2, BOS(=SELECT) 0/3, F1 0/6, F2 0/7, F3 0/8, SHIFT 1/0, CTRL 1/1, CAPS 1/2, GRAPH 1/3, CODE-KANA 1/4, CLR 2/0, UP 3/0, DOWN 3/1, LEFT 3/2, RIGHT 4/2 (inferred col for RIGHT — verify against the Red Book appendix before shipping; the setter API is the contract, the position is data), BS 5/0, TAB 5/1. The full 8×10 table lives in msx_kbd.h as one generated array — no parallel table.

Joystick: port A via PPI A bits — A: 0=TRGA, 1=up, 2=down, 3=left, 4=right; B: 6=TRGB, 7=up/down/left/right combined per pin wiring (first core: bit 7 = TRGB-alt; document in tronmsx.h verbatim). Idle level = high (inputs read 1 when released). Pins up/down/left/right for port B map to PPI A bits 5/… in the Red Book table — the core MUST ship one fixed mapping, name it in the header, and the acceptance test (AV-7) checks only that set/release round-trips through the BIOS STICK() read.

Part 3 — BIOS & Boot

3.1 BIOS Contract

The emulator core MUST NOT reimplement BIOS routines: it loads C-BIOS (or the user's real BIOS from settings) into page 0 and the game runs against it. The core owes the BIOS exactly four things: a correct Z80 (Part 2.1), a correct slot/port decode (1.3), 64 KiB RAM (1.2), and the NMI/IRQ generators (2.1). Required C-BIOS entry points that the first-core test suite calls, with the canonical MSX addresses (proven): CHPUT 0x00A2 (E = char, CALSLT-style when not in page 0), CHGET 0x009F, SCREEN 0x0044, INISCR 0x0152, LDIRMV 0x00B4, BLTI 0x01AA, GTFSZ 0x015D, KYORK 0x014B, STICK via vector table, WLDREG 0x017C (PSG register write), RDPAT 0x017F, SETVDP 0x006F, WRITEV 0x00DB.

Cross-page call — CALSLT pattern (proven; every game uses it): 

        di
        pop hl : pop de : pop bc : pop iy : pop ix : pop af   ; push args in reverse
        jp page0_rst_0x30                                     ; BIOS hook that switches
        ; the BIOS returns with the callee's RET; standard
        ; CALLSLT (fixed page) = RST 0x10 with page byte follows

The first core MUST map RST vectors 0x00-0x38 to BIOS handlers as C-BIOS ships them; no core code may special-case an RST. The IM 2 interrupt vector table lives in RAM at I × 256; the core MUST NOT prefill it — C-BIOS does.

3.2 ROM Header & Boot Trace

Cartridge header (proven, 16 bytes at 0x4000):

4000: 'A' 'B'                 ; magic
4002: dw  entry_INIT80         ; 0 if absent
4004: dw  entry_INIT19         ; 0 if absent
4006: dw  entry_SHELL          ; 0 if absent
4008: dw  entry_BOOT           ; 0 if absent (MSX2 disk skip)
400A: dw  entry_HOOK           ; 0 if absent (NMI/keyboard hook)
400C: 00 00                   ; reserved
400E: version                 ; bit7 = ASCII statement present;
                              ; bits 5,4 = MSX2/MSX2+ machine bits; low bits:
                              ; 0=MSX1, 3=MSX1+JP, 4=MSX2, 5=MSX2+JP (proven set)

Boot trace (normative order the first core MUST produce, and AV-3 asserts):

  1. CPU reset: PC=0000, I=0xFF→IM1, AF/BC/DE/HL = 0xFF, SP = FFFC (Z80 law), all ports idle.
  2. BIOS (C-BIOS) initializes VDP registers, sets SCREEN 0, clears VRAM.
  3. BIOS scans page 1: header AB at 4000h and, in page 2/3 at 4000h+0x4000 offsets, validates; selects INIT80 path for 32 KiB ROMs.
  4. CALL INIT80 (HL=3 = ROM present, return values: 0 run, 1 chain next slot, 2 BASIC, ≥3 = treat per MSX law: 4 = ASCII-only skip). Then INIT19, then SHELL.
  5. If INIT80 returns 0: BIOS leaves control to the cartridge; the game loop runs against VDP + PSG as specified here. If no cartridge: C-BIOS BASIC banner.

The NMI hook vector HOOK and keyboard-hook vector are set by the cartridge via BIOS SETKEY/SETHOOK (0x0045 region); the core MUST call whatever address the BIOS NMI chain reaches — it never calls cartridge code directly.

Part 4 — Real Body & Launch

4.1 BMSX Record (normative byte layout)

An MSX program is a first-class real-body, not a side folder (hypermedia discipline, hypermedia_dnd). The record is fixed and versionless so host C99 can read it without a parser framework. All fields little-endian; total header 64 bytes, followed immediately by size payload bytes.

    char     name[32];
} b_msx_body;               /* sizeof == 64; static assert in msx_body.h */

Validation law (AV-1 tests each): kind=1 requires payload[0..1]=='AB' and size ≤ 32768 for the first core (larger ⇒ MSX_ERR_HDR until MegaROM lands); kind=2 requires entry == 0x0100; kind=3 payload MUST begin with the BLOAD header byte 0xFE; kind=4 MUST be a legal .cas (block records: 0x00 header / 0x01 data / 0x02 EOF per TACS). Disk and cassette images are child real-bodies referenced by their own records, never strings baked into a ROM.

A virtual-body in a document or on the workbench points at the real-body by path exactly like every TAD body; opening it is the launch path below.

4.2 Launch Algorithm

Opening the virtual-body creates one BTRON window and starts the machine. No separate emulator process, no “pick a file” step. Normative sequence:

  1. Read + validate the BMSX record (4.1 law). Fail ⇒ error window, never a silent hang.
  2. Resolve settings: bios.msx2p, bios.msx2pext, bios.disk, bios.kanji, machine (default MSX2+). Record's bios_key overrides the default key name (not its value). Missing BIOS ⇒ window naming the key.
  3. Create the BTRON window: title = name, client area 512×424 (MSX2+ ×2) or 256×212 (×1). Menu: reset, pause, disk slot, quit — BTRON menu parts, not an emulator UI.
  4. Build the machine: Z80 at Z80_HZ, 64 KiB RAM, V9958, PSG, PPI; map BIOS into page 0, insert program per kind (rom→page 1, com→drive A once disk lands, first core accepts only rom and returns MSX_ERR_KIND for 2–4 with a clear note).
  5. Reset and run. The first presented frame is after the BIOS handoff (INIT80 trace, 3.2) — the window MUST NOT show a firmware menu unless flags bit0 (pause at first frame) is set.

5.2 Threading & Rings (normative)

tasks: MSX_UI   (window events; kbd setters, cmd enqueue)
       MSX_CORE  (msx_run_frame loop + psg_submit drain; IOD plane)
       MSX_AUDIO (virtio_sound_write pump; B-Audio consumer)
rings (all static, single-producer/single-consumer):
  cmd_ring   16 × { uint8_t cmd; uint32_t a0; }   cmds: RESET, PAUSE, RESUME, KBD_SYNC, QUIT
  pcm_ring   4096 × int16_t stereo frames         producer MSX_CORE, consumer MSX_AUDIO
  input slot 24 B: { uint32_t seq; uint8_t kbd[10]; uint8_t joy; uint8_t rsv[7]; }
               writer MSX_UI, reader MSX_CORE — the ONLY host-to-machine data channel
  fb         3 planes, 108,544 B each             B-Media IOD budget (Part 6), NOT core statics;
                                                  writer MSX_CORE, reader MSX_UI blit

Input travels through the slot, not the ring: an 8-byte cmd entry cannot carry an 80-bit matrix, so KBD_SYNC is the per-step tick marker whose a0 is the slot's sequence number, and the matrix itself is the one published snapshot (8 rows × 10 columns plus joystick, 2.5). MSX_UI writes payload then seq; MSX_CORE reads seq, payload, seq again and re-reads on mismatch — a seqlock, no mutex, and exactly the "ownership moves by message, not lock" discipline of B-Core. Level-driven and single-slot means a dropped tick cannot desynchronise state: the next step simply sees the newer matrix, and the debugger logs what it actually saw (8.2).

The MSX_CORE loop paces itself on msx_run_frame wall time vs 16.67 ms. It MAY skip the presentation of a frame, but it MUST NOT ever run a step with a cycle count other than T_PER_FRAME: catching up is two consecutive steps of exactly T_PER_FRAME T, each with its own input snapshot (8.1 D1), never one step of two frames' cycles. Never sleep mid-frame. PCM back-pressure follows the B-Audio telemetry law exactly: write while virtio_sound_get_queued_bytes() < 2 × PUMP_CHUNK; drops are counted, never blocked. The cmd ring full ⇒ counted drop (B-Core rcv EMPTY semantics), and a dropped KBD_SYNC is recorded in the input log rather than retried — the log is the record of what the machine saw (D5, 8.2).

7.2 toolchainMSX — Rasm as assembler, z88dk as compiler and linker

toolchainMSX is the name of the shipped Z80 build kit: Rasm as the assembler, z88dk (zcc + z80asm + appmake) as the compiler driver, linker and packager, and msxpak as the thin C99 real-body wrapper. C++ remains prohibited inside the BTRON boundary (0): tronMSX, msxpak and the harness are C99 with zero runtime heap, and Z80-side C is C99 (see the front-end rule below).

This supersedes the design note's Pasmo-only policy, and the two reasons are architectural, not taste:

  • License. Pasmo is GPL; Rasm is MIT and z88dk is Clarified Artistic. The kit can therefore be vendored straight into the B-System tree with no copyleft exposure, and Rasm is C — it fits the boundary instead of sitting outside it.
  • A real linker. Pasmo emits no relocatable objects, which forced the kit into "one ORG, one invocation, one target". z80asm links sections and libraries, so multi-file C + asm builds, sections, and library code become honest instead of hand-rolled; appmake already emits the emulator artefacts (.cas, .dsk with a .com, ROM image) that 7.5 requires.
  • Debug surface. Rasm exports symbol and breakpoint files plus makefile deps — the exact input the openMSX Symbol Manager reads and the input tronMSX's time-travel debugger needs (Part 8). One symbol artifact, both tools.

The one thing z88dk must not be allowed to keep is its own C startup. z88dk's +msx target is the classic library and its BIOS-shaped CRT owns the first bytes, which collides with the BMSX contract in Part 3/4. Normative resolution: toolchainMSX ships its own startup — toolchainMSX/crt0_btron.asm (Rasm syntax) written into the cartridge header at 0x4000, linked with -crt0=crt0_btron.asm, and built -Ostandard (never -Omax), so toolchainMSX's CRT obeys the boot trace in 3.2. Front-end rule: C99 conformance comes from -compiler=sdcc -clib=sdcc_iy; sccz80 (near-C90) is NOT approved for new C sources. Library rule: the classic library is used only for I/O and memory-move helpers over the fixed 16-byte-pointer conventions of MSX BIOS; malloc from the classic library MUST NOT be linked into a BMSX program (AV-11 asserts the absence of the symbol). The heap is a static pool declared by the program itself if it wants one — declared, bounded, and living in its own .DATA/.BSS; the BMSX record (4.1) carries no heap field and MUST NOT gain one for this. Inline BIOS calls stay in Rasm assembly.

Part 8 — Time-Travel Debugger (normative goal)

openMSX's reverse and step-back (7.1) is the one feature this book does not concede to an external process. B-MSX ships a frame-granular time-travel debugger: step backwards frame by frame, jump to any frame in the window, stop on a PC breakpoint or a page watchpoint, and read the Z80 / VDP / PSG state at the historical instant — inside the BTRON window, from the same real-body. It is a stated goal of the project (Part 0) precisely because the core is small and deterministic: reverse execution here is a consequence of the machine model, not a layer bolted on top of it. Everything below is normative for the debug shape; 8.5 states exactly what the shipping shape excludes.

8.1 The determinism law (D1 … D7)

The single equation the debugger stands on, stated so the tests can attack it:

state(N+1) = step( state(N), input(N) )

  step   == msx_run_frame()   — exactly T_PER_FRAME T, nothing else (5.1, 5.2)
  input  == the published snapshot in the input slot (5.2), logged as 16 B per step (8.2)
  state  == RAM + VRAM + Z80 + VDP + PSG + PPI + slot map + timers: the checkpoint of 8.2
  • D1 — no host clock inside step. The pacing loop may read wall time to decide when to run the next frame; that reading MUST NOT change how many T the frame runs. Catch-up is two consecutive steps of T_PER_FRAME (5.2), never one step of double length. Consistent with 1.1: the VDP phase already MUST NOT read the host clock.
  • D2 — no randomness. rand, random, arc4random and time-seeded state MUST NOT appear in any step-path translation unit. The machine's only pseudo-random source is the PSG noise LFSR, and it starts at the fixed 0x0ACE state (2.4, proven).
  • D3 — no undefined state. msx_init zeroes every array it owns before the first step; msx_reset re-establishes the complete reset register set (2.1); first-core RAM initializes to 0x00 (inferred — openMSX defaults to 0x00, blueMSX varies; the value used is recorded in the checkpoint header so a golden file names its own initialization). Unmapped/floating bus reads still return 0xC0 (1.3).
  • D4 — integer-only step. No float, double or libm call on any path that can reach machine state. The PSG resampler is 32.32 fixed-point (2.4) and the renderer is integer (2.3) already; the law exists because the host FP environment is invisible state that would leak into samples and pixels and defeat replay equality.
  • D5 — back-pressure never reaches hardware. B-Audio telemetry may change how many PCM frames are handed to the host; it MUST NOT change a PSG register, a phase accumulator or the LFSR. A cmd_ring overflow is a host-timed event, so it is recorded in the input log and replay sees exactly what the live run saw: the log, not the queue, is the truth.
  • D6 — inputs are level snapshots. Keyboard and joystick enter the machine only through the published input slot, read once per step and ticked by KBD_SYNC (5.2, 2.5), never as host-timed edges. UI events mutate the slot; step reads the slot, and the read is what gets logged.
  • D7 — ROM and BIOS are hashed, read-only inputs. msx_load_rom and the BIOS loader compute FNV-1a 64 over the exact bytes mapped into the machine (offset basis 14695981039346656037ULL, prime 1099511628211ULL, byte-at-a-time) and expose it as msx_body_hash() (5.1). ROM writes are discarded (1.2), so the hash cannot drift mid-run — it is what makes a checkpoint trustworthy.

D1–D7 bind the core from its first commit, before any debugger exists: violating one is not a missing feature but a machine that cannot be trusted to replay, and AV-9 measures it on the plain emulator. One structural consequence: a frame MUST be steppable headless — no window, no SDL, no plane write, PCM discarded — because that is what replay is. Presentation stays outside step by construction, which 5.1 already guarantees by keeping blit and PCM submit as separate calls.

8.2 Input log, checkpoints and the replay algorithm

Two static structures make the law rewinding. The input log records the machine's entire host-visible history in 16 bytes per frame; the checkpoint ring stores full machine snapshots so rewind is a restore, not a re-simulation from power-on. 

typedef struct {            /* one record per EXECUTED step (not per presented frame) */
    uint8_t  kbd[10];       /* the whole 8x10 matrix as the step sees it (2.5), 80 bits */
    uint8_t  joy;           /* TRGA / TRGB / steering bits, level snapshot (2.5) */
    uint8_t  cmd;           /* cmd_ring byte consumed this step: RESET|PAUSE|RESUME|QUIT|none */
    uint8_t  drops;         /* bit0 pcm drop, bit1 cmd drop — D5: host-timed events are data */
    uint8_t  pad[3];        /* zero; keeps the record 16 B and the row math a shift */
} tt_input_t;               /* sizeof == 16; static assert in tronmsx_tt.h */

log ring: 65,536 records × 16 B = 1,048,576 B (exactly 1 MiB)
coverage: 65,536 frames / 60 Hz = 1,092 s = 18 min 12 s of inputs

A checkpoint is the whole machine, fixed-size, and its header is as normative as the BMSX record (4.1): byte offsets pinned by tt_state.h static asserts, all fields little-endian, header 256 B followed by RAM then VRAM.

ROM and BIOS bytes are deliberately not in the snapshot: D7 makes them inputs identified by hash, so a restore against a different body is refused rather than silently wrong. Everything a game can see is inside — the palette, sprite attribute and name tables live in VRAM (2.3), so the 131,072 B block carries them with no extra header fields. The ring is TT_RING_DEPTH == 64 checkpoints == 64 × 196,864 == 12,599,296 B (~12.0 MiB), and three interval profiles trade coverage against seek distance — the memory is identical in all three, only the arithmetic of the window changes:

Invariant (static-asserted, AV-10): the deepest profile MUST stay inside the input log — 38,400 ≤ 65,536 frames — so a seek inside the checkpoint window always has its inputs available. If a later revision widens the interval, it widens the log in the same commit.

Restore and replay, normative order:

  1. Pick the newest checkpoint K ≤ target; verify header magic, version, CRC32 and msx_body_hash() before touching the machine. A failed verify leaves the machine exactly as it was and returns MSX_ERR_TT_STALE; a target older than the ring head returns MSX_ERR_TT_RANGE. No partial application, ever.
  2. Copy the 65,536 B and 131,072 B blocks back, then the 256 B header fields into their live variables (single-threaded on MSX_CORE at a frame boundary — see 8.3's pause rule).
  3. Flush pcm_ring and reset the PSG phase accumulators to the restored values, so no sound from the discarded future plays, and the next frame's PCM is the historical one.
  4. Replay forward from K to the target: for each frame, feed tt_input_log[frame] into the machine, run exactly one msx_run_frame-equivalent step headless, no blit, no PCM submit, no pacing sleep.
  5. Render once from the restored VRAM to present the target frame. Rendering is derived from VRAM state, not from CPU execution, so TT_STEP back-by-one needs no replay at all — that is what buys the 8 ms budget in 8.5.

8.4 Breakpoints, watchpoints, symbols — one artifact, two tools

toolchainMSX (7.2) emits a symbol artifact per build: Rasm's symbol export for assembly, z88dk's map for C. Their file spellings differ, so the kit normalizes both into one fixed record with mssym (7.6) and the debugger reads only that: 

typedef struct {            /* 32 B, one hand-written truth for label -> address */
    uint16_t pc;            /* Z80 address */
    uint8_t  page;          /* 16 KiB page index 0..3; 0 for the first core, MegaROM later */
    uint8_t  kind;          /* 0=label 1=code 2=data */
    char     name[28];      /* NUL-terminated */
} tt_sym_t;                 /* table: 8,192 × 32 B = 262,144 B, static, sorted by pc */
  • Breakpoints match, never patch. The debug shape exposes an instruction-boundary hook inside the step loop; a hit compares the returned PC against ≤ 16 entries. Writing 0xFF into a ROM page to trap a PC — or ld b,b patching — is forbidden: it would violate D7 and corrupt the very history being examined. The two-step hook costs a bounded number of compares per instruction, which is exactly why it exists only in the debug shape.
  • Watchpoints are (page, offset), not absolute addresses, because in MSX an address is a slot decision (1.2/1.3): 0x8000 is whatever page 2 currently maps. The bus access check uses the mapped page index, so a watch survives bank switching. DBG_BRK / DBG_STR (7.4) remain the in-program instruments and land in the window log stamped with their frame number; every log line is therefore clickable and rewinds the machine to the instant it was emitted. That coupling — source instrumentation and historical seek on one timeline — is the actual payoff of Part 8.
  • Inspector views (MSX_UI, plain BTRON parts): disassembly of PC ± 8 bytes from a static opcode table in the shape of the superzazu core's mnemonics — not a copy of openMSX's GPL R800Dasm.c (license fence, 7.7); register panel from tt_state; VRAM tile/bitmap dump through the 2.3 renderer; PSG register panel with the 2.4 mixer/envelope decoding; input-log strip showing which frame each key press entered.
  • Symbol parity is a conformance claim, not a convenience: the same game.ttsym loads into the openMSX Symbol Manager for cross-checks, so a disputed address means the same thing in both tools.

Latency model (inferred constants, pinned by AV-10). Step-back one frame in TT_STEP = validate (CRC32 over 196,864 B, plus an 8-byte hash compare) + restore (memcpy 196,864 B) + one render pass from VRAM. At ≥ 1.5 GB/s copy and ≥ 500 MB/s CRC on the desktop POSIX host that is ≈ 0.55 ms of work; the normative budget is ≤ 8 ms end-to-end including the inspector's state panel, which is what makes stepping feel like stepping. Long seeks add replay: the headless replay floor is ≥ 2,000 frames/s on the desktop host and ≥ 600 frames/s on the Pi 400 class target, so TT_WINDOW's worst case is 29 frames ≈ 15 ms desktop / ≈ 48 ms on the small target, and TT_SESSION's 599-frame worst case is ≈ 0.3 s desktop / ≈ 1 s on the small target — acceptable because a profile seek is a deliberate act, not a keystroke. The floor is 20× the AV-8 real-time requirement and inherits its instruction-cost model; if a target cannot reach it, the interval profile is narrowed, the law is not.

8.6 What the debugger deliberately does not do

  • No instruction-granular reverse. The unit of history is the frame. Per-instruction pause exists (8.4); per-instruction undo does not, and no revision of this book should pretend the memory math changes: 60 snapshots per second of 196,864 B is 11.8 MB/s of ring traffic.
  • No rewind of host-visible effects. PCM already in the B-Audio queue is flushed, not reversed; plane history beyond the triple buffer is gone; the window's own state (menus, other windows) is not part of the machine and is never restored.
  • No persistence into the real-body. A BMSX record is a program (4.1), not a save state. Checkpoint files live in the kit's build directory, are not child real-bodies, and shipping them with a program is out of scope. A deliberate save-state feature would need its own vector and its own law about D7 hashing.
  • No second machine, no external protocol. One machine instance per process (5.1) and no gdb-stub / remote wire protocol: the debugger is the B-MSX inspector. When a cycle-level dispute needs a third party, openMSX remains the oracle (7.1) and the one-binary law (7.5) is what lets the same ROM be re-run there.
  • No R800, MSX-Audio, MegaROM bank or disk state in the snapshot while those units are outside the first core (Part 0). Adding one adds header fields and its own AV delta — the 256 B reserved runs (224, 200) exist so this is additive, never a renumbering.

Verification Status (honest account)

B-MSX ships as a specification: doc/md/MSX.md is the origin note, this book is the normative shape, and no src/emulators/msx/ exists in the tree yet — so every AV-vector is currently labeled NOT BUILT, not PASS, and neither test-msx, msx-test nor msx-tt exists as a make target. Part 8 is in the same state as the rest: the determinism law is a commitment the core must honour from its first commit, not a description of existing code, which is exactly why it is written here before tronmsx.c is. There is no Coq/OCaml model for the emulator core and this book deliberately cites none. Requirements inherited from verified neighbours: the five-call alphabet and counted-drop laws (media_intercore), SMP/AMP plane budgets the loop must obey (media_smp), buffer/refcount discipline for streams (media_rtp), and the real/virtual-body semantics (hypermedia_dnd). Constants labelled proven are pinned by the MSX standard, the Z80/V9958/AY manuals, or C-BIOS behaviour and become testable at build time; constants labelled inferred (VOL16 curve, RIGHT-key column, flash period simplification, ROM-size caps, speed budget, RAM init byte 0x00, the 8 ms step-back budget, the ≥ 600/2,000 frames/s replay floors, the ≤ 16 MiB debug cap) are first-core choices explicitly open to calibration without invalidating anything else. What is not calibratable is the arithmetic of Part 8: 196,864 B per checkpoint, 16 B per input record and the 64-deep ring are static-asserted numbers, because a snapshot format that drifts silently is a debugger that lies.
