前提: なし（この節）／ Uses: nothing yet — this section only declares how the rest is written.
Why the order is the content. A manual that lists buttons first teaches memorisation. This one teaches a vocabulary: a bar, a tick, a slot, an insert, a budget. Every later chapter is written with those words alone, so that a reader who has finished chapter five can read chapter nine without a dictionary and without a guess. The division of languages follows the same rule. Japanese describes what the desk does when it is used. English states why it does it that way and what would break otherwise. Neither layer repeats the other.
Where the numbers come from. Every figure printed here — 73408 bytes, 48 slots, 632 µs, 32 programs, 960 ticks — is a figure the running program can print itself, and each is stated in the specification doc/txt/ORCHESTRA.txt and implemented in src/media and src/demo. 第1章 材料 — 装置と三つの層 (Foundations)

前提: なし。この章は装置・層・四つの数だけを定義する。以降の章はここで出た語を使う。

1.1 三つの実践 — Rock・Classic・Orchestra

Orchestra はステージ用の DAW です。想定する使い手は三つに固定されています。Rock は生バンド（キック、スネア、ハット、ベース、ギター、キー、リード、ボーカルの八トラック）。Classic は声と古典楽器（ボーカル、ピアノ、フルート、バイオリン、チェロ、コンティニュオの六トラック）。Orchestra はフィルハーモニーの配置（第一バイオリンから打楽器まで十六のモノフォニックトラック）。この三つ以外の用途を、この案内書は扱いません。同様に、チューナー、Logger、Click & Cue、Router、レコーダ、Monitor、シーンマネージャといった別商品は存在しません。Orchestra の診断は窓ではなく、デスクの上の一行のテキストです。
Three practices, not a market. Orchestra is the only DAW specification in B-System, and it is written for a fixed set of users rather than for a general audience. The reason is structural: the tone of every sound is produced by a hand-written procedure, and a procedure has to be chosen, tuned and budgeted. Three practices give thirty-two programs that can be named, measured and defended. A fourth practice would mean a second set of procedures, a second budget, and a second manual. Diagnosis is text on the desk rather than a separate product for the same reason — an extra window is an extra layer of promise that the desk itself already has to keep.

1.2 四つの固定された数

Orchestra を使ううえで暗記が必要な数は四つだけです。1 サンプルレートは 48000 か 44100 の二択で、既定は 48000。2 ホスト周期は 1024 フレーム（48000 で 21.3 ms、44100 で 23.2 ms）。3 合成の量子 Q は 32 フレーム。4 セッションファイルは 73408 バイト。この四つは設定項目ではなく、コードのリテラルです。wanted.samples = 1024 は virtio_sound_open のなかに書かれていて、Q は RENDER_BLOCK の 32、73408 は 128 + 64×96 + 16×100 + 4096×16 です。

音の出口は virtio サウンドの五つの呼出だけです。呼び出しは open・write・close・is_ready・get_queued_bytes。装置から読む呼出は存在しません。回線は int16、_INTERLEAVE（L,R,L,R）、little-endian。open はすでに使用中の装置を乗せ替えます。周期を取り出す呼出はないので、周期は上の固定数として扱うほかありません。
The four numbers are not dials. A conventional DAW offers a buffer-size slider, a sample-rate picker and an import size. Orchestra offers none of them, because each would move a deadline that the admission test in chapter five has to compare against. Fix the host period at 1024 and the block quantum at 32, and "did the graph make it?" becomes an arithmetic question with one answer per sample rate. Fix the session file at 73408 bytes and a file can be validated by its length before a single byte is read. The missing read path is a fact of the driver, not an omission of the desk: audio leaves, and the only thing that comes back is the depth of the queue.

Arrows only point down. The layering rule is enforced by includes, not by review: the desk cannot reach the device, and the media cannot reach the window system. 第2章 音楽時間 — 拍・チック・音高 (Musical Time)

前提: 第1章のサンプルレートと量子 Q。この章のチックは第九章の SMF まで一直線に使われます。

2.1 拍・小節・テンポ

拍（beat）は BPM が数える単位です。BPM は 40 から 240 までの整数、分子 num は 1 から 12、分母 den は 2・4・8・16 のいずれか。拍は分母の音符です。den が 4 なら拍は四分音符、8 なら八分音符、2 なら二分音符、16 なら十六分音符。小節の長さは拍の num 倍です。
式1 T_beat = 60 / BPM T_bar = T_beat × num T_quarter = T_beat × (den / 4) = 15 × den / BPM

例: 96 BPM・6/8 なら T_beat = 0.625 秒（八分音符ひとつ分）、T_bar = 3.75 秒（小節に六つの八分音符）、四分音符は 1.25 秒。

Why the denominator defines the beat. Counting the beat as the note the denominator names, rather than always as a quarter, is what makes 6/8 unambiguous: at 96 BPM a 6/8 bar is 3.75 s, six eighth-notes, exactly what a player expects. The cost is that "quarter note" is no longer a constant duration, so the desk keeps one extra factor — den/4 — wherever a quarter is meant. The tempo range 40–240 is a validator, not a preference: outside it, the session file is refused (chapter nine) and a menu change is refused with the counter refuse_tempo.

2.2 チックとスナップ

Orchestra の内部時計は ORCH_PPQ = 960 チック／四分音符です。拍あたりのチックは 3840 / den、小節あたりは num × 3840 / den。編集グリッド（snap）は四つの量子だけを持ちます。
式2 snap(t) = floor(t / q) × q BAR = num × 3840 / den （小節） BEAT = 3840 / den （拍 = 分母の音符） 8TH = 480 （固定） 16TH = 240 （固定）

6/8 では BEAT と 8TH の量子が一致します（どちらも 480 チック）。

チックとサンプルの変換は整数演算だけです。float の音楽スケールは存在しません。
式3 sample(tick) = floor((tick × f_s × den + 32 × BPM) / (64 × BPM)) 式4 D = 64 × BPM tick(N) = floor(((N + 1) × D − D/2 − 1) / (f_s × den)) 検算: f_s = 48000, den = 4, BPM = 128, tick = 40 → sample = 938 sample 938 → tick 40（40.04）, sample 937 → tick 39

MIDI クロックは常に 24 パルス／四分音符（インターバル 40 チック）で、拍が四分音符でないときも変わりません。0xF8 はどこにも出力されず、OrchView.midi_clock のカウンタだけが増えます。

Integer time, twice. The two conversions above are the only place where musical position becomes memory position, and they are integer in both directions so that a tick round-trips to itself. A float scale would let a session drift between the arrange grid and the file; the worked check (tick 40 → sample 938 → tick 40) is printed in the specification precisely because rounding is where a naive implementation fails. The half-denominator offset in equation 3 is not cosmetic and cannot be moved by rearranging the division. MIDI clock stays at 24 per quarter because that is the wire convention, while the desk's own grid stays at 960 — the two are deliberately not the same number.

2.3 音高 — 12平均律と転調の列

音高は 12 平均律です。MIDI キー n は 0 から 127。
式5 f(n) = 440 × 2^((n − 69) / 12)
実際に鳴る音は、四つの段を経て決まります。① トラックのキー分割（key split）が [key_lo, key_hi] の外を捨てる（lo=0 かつ hi=0 は 0..127 と読む。分割は 0..127 / 0..59 / 60..127 の三位置を orch_cmd_split が mod 3 で回す）→ ② トラックの transpose → ③ プログラムの transpose → ④ 0..127 へクランプ → 式5。ただし式5 は呼び出しごとに powf を計算しません。s_pitch[128] の表を起動時に一度だけ埋めます。
Why a table and a clamp. Frequency is computed on the hot path, so it is a lookup, and the lookup has to be bounded before it is indexed — hence the clamp to 0..127 after both transposes. The split zone is a three-position switch rather than free ranges because the file stores exactly two bytes (key_lo, key_hi) and the desk must never offer a control the container cannot carry.

2.4 ベロシティ・音量・パン

強弱は速さ（velocity, v_m = 0..127）から振幅へ換算します。u = v_m / 127、領域は 0.08–0.45、カーブは vel_curve の 0・1・2 の三つです。
式6 v0 = 0.08 + 0.37 × u （線形） v1 = 0.08 + 0.37 × √u （遅い立ち上がり重視） v2 = 0.08 + 0.37 × u² （強い打鍵重視） 式7 G_trk = 0 （volume = 0 または mute） G_trk = 0.08 + 0.37 × (volume / 127) （それ以外） 式8 p = (CC10 − 64) / 64 ∈ [−1, +1] G_L = cos(π/4 × (p + 1)) G_R = sin(π/4 × (p + 1))

pp 0.08–0.12 / mp 0.14–0.18 / mf 0.20–0.26 / f 0.28–0.36 / ff 0.38–0.45 は、すでに計算された v の帯域名であり、別の曲線ではありません。式7 で volume 64 → 0.2665、40 → 0.1965。CC127 は p = 63/64 で +1 には届きませんが、式はそれに合わせられません。

One scale, three curves, no second curve. Velocity shaping is the only place a performer's touch reaches the sound, and it is deliberately a single linear family with three exponents. There is no hidden curve that recentres 64 into the middle of the mf band: the numbers above are what the desk computes, so a mixer reading of "64 is mf" is a reading of the same line, not of a second model. Pan follows the equal-power pair, and CC10 maps onto it with the MIDI range, which is why the extreme right is 63/64 rather than 1. The desk keeps the honest value instead of rescaling the formula to hide it.

A program is a call site. The desk has no synthesis engine of its own and no sample library; a program is a row that names an existing procedure and the data that procedure needs. That is why there are 32 programs instead of 128: each row had to be measured against the block budget of chapter five before it could be published. The single exception worth learning is program 98, Bell, which goes to a two-operator FM voice rather than to the partial-shim dispatcher — the ratio and index below are the paper's pair, 2.76 and 1.8, not an invented one. Refusing the other 96 GM numbers is a deliberate act: an unmapped number that silently picked a default instrument would make a session file mean one thing on the desk and another on paper.

3.2 声の割り当て — 48スロットと盗み

DAW 側のスロットは s_slot[48] の静的なプールで、ひとつのスロットはひとつの MIDI 音符です（部分音ではありません）。合成器自身にも MAX_VOICES 48 が別々にありますが、数字が一致するだけでプールは別です。割り当ての順序は「空いていれば取る」ではありません。
式9 proxy(slot) = gain × exp( −(npos − t0) / f_s ) （τ = 1 秒） ① トラックの占有人数 ≥ poly → 同じトラックの式9で最も静かなスロットを盗む ② そうでなく、空_slot があれば index 小から取る ③ 空がなければ、全プールで式9の最静音を盗む（track = −1 で探す）
poly はロード後の天井で、ファミリーはこれを下げるだけです。Rock と Orchestra は全トラック 1、Classic はプログラム 0（ピアノ）だけ 6、ほか 1。盗みは steal_voice を増やします（書き出し中を除く）。黙らせたスロットは wa_release_bus_key(bus, key) と、ベルなら lilcu64_voice_release で消えます。シムを呼んだあと何も起きなかった場合（ノードが採れなかった等）は、スロットをプールへ戻して shim_landed がノート refused を数えます — この場合だけ、戻り方が「ハング」ではなく「返却」になります。
Stealing is defined by loudness, not by age. The desk ranks a held slot by the product of the gain written at note-on and an exponential decay with a one-second time constant. Age alone would cut a long piano note that is still audible, and gain alone would keep a note that has already faded to nothing; the product is the honest proxy for what the listener can still hear. The per-track ceiling is checked before the global one, so a busy track cannot starve its own channel by reaching into another track's notes first. During WAV export the same steals happen but are not counted, because a render artifact must not depend on who is listening.

3.3 ワンショットとノートオフ

Percussion length belongs to the instrument. This keeps a hi-hat from being truncated to the length of a mouse drag and matches the shim bodies that already exist. The consequence the manual must state plainly: an event drawn with the pencil gets the length of the snap quantum, not the instrument's fixed length, except when the row is a shot and the pass is the armed record pass, where the event's own duration wins.

第4章 インサートとホール (Inserts and the Hall)

前提: 式13 のビクヮード（第3章）、G_trk とパン（第2章）、小節と拍（第2章）— ディレイの長さは十六分音符の長さから決まるためです。

4.1 インサートは要素ではなく位置

インサート（挿入エフェクト）は九つの id です。ORCH_INS_BYPASS = 0、EQ = 1、SAT = 2、DELAY = 3、REVERB = 4、CHORUS = 5、GATE = 6、TREMOLO = 7、LIMITER = 8。 tenth はありません。インサートはグラフの要素ではありません。要素なら、第六章のトラック64本が第五章の上限16を突き破ってしまうからです。トラックには二つまで（ins0 と ins1）、マスターには一つだけ（master_lim）で、マスターが許す値は LIMITER と BYPASS の二つだけです。他を指定すると refuse_insert が増え、状態はそのまま、ステータス行に "insert" が出ます。
The slot imitates a VST slot, not its format. A binary plug-in host would need a loader, allocations on the hot path and a heap — three things the real-time contract forbids. So the insert is a place in the chain whose algorithm is chosen from a closed catalogue of eight, and the catalogue is closed because each entry has a state budget. The ninth id, LIMITER, is reserved for the master and enforced at the setter, not at the renderer, so the desk cannot get into a state it cannot play.

One hall, because a hall is memory. The reverb is four comb filters and four all-passes per channel, with line lengths scaled by s_sr/44100 and two delay buffers fixed at 44100 samples. 第5章 グラフと予算 (Graph, Budget and Latency)

前提: 量子 Q とサンプルレート（第1章）、スロット（第3章）、インサートとホール（第4章）。この章の「周期 T」が第七章の拒否と第十一章の比較で使い直されます。

So the topology is a constant: the ten names, the two tee branches, the bus list and every buffer are fixed at boot. The ceiling of sixteen elements is a ceiling on names, not on bodies — each body is one function in render_graph. An insert is not an element for exactly this reason: sixty-four tracks with slots would blow a limit placed on the vocabulary.

5.3 ペーサー — 追い付きは64回まで

音を回す入口は三つに分かれ、共用の tick はありません。orchestra_ui_tick() は UI の一周に一度（六か所）、orchestra_audio_service(now_us) はキャセットの呼出しと同じ場所で、orchestra_audio_tick() は中の専用です。

動作点は「追い付き中は1周期未満、テンポを保っているときは1〜2周期」。4へ足して埋める経路はありません。 別個のオーディオ面と SCHED_FIFO はこのビルドには無く、保証は上の合計と追い付き上限です。

Catch-up is bounded, and so is silence. The pacer can render at most sixty-four blocks per call, so a stalled host cannot make the desk spend unbounded time in one loop, and the two queue thresholds keep it from writing into a device that is already full. There is no separate audio thread in this build: the audio actor is driven from the same UI passes that paint the desk, which is exactly why the guarantee is the published sum rather than a scheduler priority. If a single invariant ever fails, orch_check raises a sticky flag and every later block returns REFUSE — the desk goes quiet instead of clicking.

5.4 聞こえる遅れ — 三つの長さは交換しない

「遅延」という語は三つの別々な長さに使われます。混ぜないでください。
① ブロックの予算

632 µs の WCET を 666 µs（48000）または 725 µs（44100）の周期に収める、という算数。音の遅れではなく、間に合うかどうかの話です。

② INPUT 面

周期 1000 µs・予算 500 µs。MIDI 配送がこの中で戻る、という約束。ただし本ビルドでは配送の呼出元がありません。

③ 聞こえる遅れ

queued_frames / f_s。デバイスに残っているフレーム数を実際のサンプルレートで割った、測定された値です。

④ 参考：ホスト周期

1024 フレーム = 21.3 / 23.2 ms。メニューの「バッファ」は "Q 32 | host 1024" と出しますが、これは定数の表示で測定ではありません。

プルトが出す ms は測定値だけです。UI の一周が毎回 gst_rt_queued_ms() を呼び、その値を OrchView.queued_ms に入れ、メニューの右端へ書き、ステータス行の "q NN ms" にも使います。「0.8 ms」のような定数表記は禁止、「0.2 ms 未満」もこの章からは導けません（500 µs は 0.5 ms、632 µs は 0.632 ms）。5〜8 ms の round-trip もこのビルドの約束ではありません — ホスト周期が1024フレームなので、それを裏切るには128フレーム以下の backend が必要で、それは virtio_sound_open の値ではありません。
Latency is a measurement, or it is nothing. Three different lengths are routinely confused in audio writing: what a block is allowed to cost, what an input plane is allowed to cost, and what the listener actually hears. This manual keeps them apart and publishes only the third as a millisecond figure, because the first two are ceilings and the third is a queue depth that changes as you play. A constant "0.8 ms" label would be a claim with no instrument behind it, so it is forbidden rather than merely avoided.

The palette is a named set because a colour written twice is two decisions about one appearance.

7.2 キー — バーが閉じているあいだの Orchestra

キー操作の解釈はメニュー部品（app_menu_handle_key）が持ち、デスクの orch_menu_key が呼みます。バーが閉じているあいだは、Ctrl + 文字が「Ctrl+X」の欄と照合され、当たった項目を実行します。Alt + 見出しの頭字は その見出しを開き、同じ Alt を開いた見出しに当てると閉じます。F2 または Menu キーは見出しを循環。Space を Ctrl も Alt もなしで押すと、バーが閉じているときに限り PLAYING と PAUSED を揺すります — これはメニュー部品の規則ではなく Orchestra の決定です。
ドロップダウンが開いているあいだは、Escape が閉じ、上下一の矢印が項目を選び、左右の矢印が見出しを移し、Return と Space が映っている項目を実行し、数字 1..9 は番号で項目を取ります。ほかのキーは開いたドロップダウンが吸い取ります。つまり「開いたメニューの中で Space は実行、閉じたデスクの上の Space は再生」という二重の意味が、どちら側でも意図どおりになります。
One key, two owners. Space is the only key whose meaning changes with the state of the bar, and the split is placed at the desk rather than in the widget so that the widget stays reusable. Every other accelerator is a table lookup in the accel field, which means an item without an accelerator (Export WAV, and every scene, window and template item) is unreachable by keyboard and is honestly listed above with "—" rather than given an invented binding.

図7-3 トランスポートの状態。locate（位置指定ジャンプ）は無く、Second Stop が唯一の「最初に戻る」です。

Play は第五章の admission を呼ぶだけ（gst_rt_set_state(PLAYING)）で、現在の N から続けます。最初のブロックは、鳴り続けている音を第5・第9章のアーミング枝で残り長さでなり直します。Stop の第一段階は PAUSED へ入り、その遷移のなかで録音リングを流し切り、ev_live = 1 の各行を snap(tick(N)) で閉じ、四十八のスロットを解き、リングを空にします。N は保持されます。第二段階は零へ戻ります — npos = 0、シムの時計も 0、内部の位相記憶も クリア、新しい home 生成番号。
テンポ・分子・分母は PLAYING 中は書けません。ボタンからもメニューからも同じ refuse_tempo になり、カウンタが 1 増えて状態行が "tempo" になるだけで、値は動きません。理屈は式3です — 走った小節の途中で sample(tick) の対応が変われば、同じ N が二つの位置を持ちます。シーン切り替えはもっと静かで、PLAYING 中はテンポ・分子・分母を拒否ではなく無視します（カウンタなし）。ゲインとプログラムは動きます。テンプレート適用もテンポを書くので、PLAYING 中は拒否です（第八章）。
Two stops because pause and rewind are different promises. The first stop must end sounding notes without losing the place — a performer pausing a passage returns to the same bar. The second must make the desk stateless again: position zero, shim phase memory cleared, and a fresh generation number so that a late block from the previous run cannot be mistaken for the next one. Collapsing the two into one button would either throw away the position or leave a half-reset clock, which is risk ten in chapter twelve.
Panic is not stop. Panic silences voices — it walks the 48 slots, skips empty ones and the metronome slot, and writes the rest to silence. It does not change state, scene, record arming or the event pool, so Panic during PLAYING leaves the transport running against a quiet pool. That asymmetry is the point: Panic answers "make it silent now", and only Stop answers "end the passage".

7.4 録音とクリック

Record は OrchView.rec の 0/1 で、どの状態でも反転できます。 武装して PLAYING になると、選択トラック（OrchView.selected）へ来た MIDI が 64 行の録音リングに積まれ、ring_apply が同じブロックでイベントプールへ写します。オーディオ録音ではなく、punch-in でもありません。書き込みは必ず snap(tick(N)) に丸められ、長押しの行は pick_dur をすぐ得ます（shot 行では note-off が何も閉じない）。
正直に書いておくこと：このビルドでは orchestra_dispatch_midi_event の呼出元がありません。つまり 7.4 が記述するのは「配線が通ったときの規則」で、実機で鍵盤を叩いても今は録音されません（第十二章 12.1）。リングが満杯なら chain_accept と chain_drop が増え、プールが 4096 に達then refuse_note_cap が増えます — 音はなって、行は足されない、という食い違いがカウンタに現れます。
Click は OrchView.click で、エンジン内では latch で写る s_lclick です。PLAYING かつ click = 1 のあいだ、閉じたハイハット系シム（key 42、ゲイン gain_of(0, 90)、長さ 0.055 秒）が一つだけ鳴ります。新しいスロットは取らず、既に click = 1 のスロットを使い回します。鳴る条件は tick(N) が ticks_per_beat で割れるところで、追い付きは 1 ブロック 4 回まで。チック 0 は小節 0 の拍 0 です。mute と solo は及ばず、固定 0.7071 を両チャンネルへ、トラックのフェーダを通さずに足します（bus 65）。
The click is a bus, not a ninth track. Reserving a slot with the click flag and summing bus 65 at a fixed gain means the metronome cannot be stolen, cannot be muted by a track, and cannot appear in the exported session as music. Four catch-up clicks per block is the same bounded-catch-up rule as chapter five's pacer applied to a musically visible event: after a stall the desk resumes in time rather than firing a burst.

7.5 シーン — 十六個の音量とプログラムのスナップショット

シーン格子はステージに八つずつ二行で並び、セルは 0..15。orch_cmd_scene が唯一の切替で、メニュー（318/319 の Send・Octave）も格子のボタン行も同じ関数を呼みます。0..15 を外れれば拒否（カウンタなし）。seqlock の下で active_scene を置き、PLAYING でなければそのシーンのテンポ・分子・分母を、それぞれの検査（40..240、1..12、2/4/8/16）を通した上で採用します。そのあと常に、そのシーンの volume[ch] を同じチャンネルのトラックへ、program[ch] を同じくトラックへ写します（push_volumes、push_programs）。255 は「変えない」、未知の番号は refuse_program を増やしてトラックを残します。PLAYING では音量とプログラムだけが動き、次のブロックから聞こえます。
すでに鳴っている音は消えず、別のシムへ乗り換えません。スロットはトラックとキーを持つが、プログラムは持ちません。インサート、P1〜P4、lighting は触りません。Octave（319）は全トラックの transpose に +12 して −36..+36 で止め、セッション全体に効きます。
A scene is a snapshot of two arrays, not a version of the score. Sixteen scenes carry per-channel volume and per-channel program — nothing else — which is why a scene change is cheap enough to be a stage grid and safe enough to be allowed during PLAYING. There is no separate scene manager product, and there is no marker object: what a conventional DAW would mark, this desk expresses as a loudness and program preset. The 255 sentinel exists because 0 would mean piano, and "leave this channel alone" has to be a third value distinct from both.

7.6 編集 — 三つの道具、四つのグリッド、Undo 十六

道具は Select・Pencil・Erase（0・1・2）で、アレンジ・ピアノ・スコアの三窓が同じ欄を読みます。表示は MIN なら「S / P / E」、それ以外なら「Sel / Pen / Era」。snap は Bar・Beat・1/8・1/16（0..3）を循環し、式2がその量子です。三つの窓にそれぞれ四つのラベルのコピー（snap_name）があることは第十二章の既知のリスクです。
Undo は UI 面だけの静的なリングで、容量は 16、動的確保はありません。行は UndoSlot（kind、track、index、n、mode、before[48]）で、種は四つ — イベント 16 バイト、名前 48 バイト、トラックの u8 欄 1 バイト、インサート（id 二つと i16 八つ）18 バイト。mode は上書き・削除・挿入の三形で、リングが満杯なら最古を置き換えます。orch_undo_apply は最新の一件だけを戻します — redo は無い。適用中は s_in_undo を立てて、戻した値が新しい行としてリングに押し返されるのを防ぎます。
ペンとゴムは PLAYING 中は書けません（orch_event_put / _del が "note" を保持して 0 を返す）。vel = 0 は新しい行にならない。イベントが 4096 枠に収まらなければ refuse_note_cap。長さが snap 量子より短ければ put が引き上げます。削除はプールを詰めて event_count を前に戻します。トラック欄（vol・pan・send・program）は field_ok（0/1 または 0..127）を通り、同じ orch_track_set_u8 から書かれ、成功時に前の値が undo へ入ります。
Sixteen undo slots and no redo is a size decision, not a missing feature. The ring is static because chapter five forbids allocation on the hot path, and it is shallow because a slot has to hold whatever it might restore — up to a 48-byte track name. Sixteen is the point where the ring stays inside a page of memory while still covering the realistic mistake ("that last phrase of notes", "the wrong program on three tracks"). Redo was dropped for the same reason the desk has no clip list: it would require the ring to be a stack with a cursor, and a cursor is a second truth about what the session currently is.

第8章 三つのテンプレート (Three Templates)

前提: 第三章のプログラムと poly_max、第四章のインサートとホール、第七章 7.3 の拒否と 7.5 のシーン。テンプレートは第七章の語だけで説明できます。

8.0 テンプレートとは何か

テンプレートはミキサの雛形であって、楽譜ではありません。三つの表（ROCK_ROW・CLASSIC_ROW・ORCH_ROW）と二つの音量表（ROCK_VOL・CLASSIC_VOL）はファイルではなくコードに置かれています。適用するとトラックとシーンが置き換わり、テンポ・拍・ホールが定まり、イベントとインサートの値線はゼロになります。apply_fam は seqlock の中で blank_music → 表の読み込み → family_fields を行い、seq の外で wa_set_reverb・lc_insert_reset・gst_rt_return_zero・gst_insert_touch を呼ぶ。トラックの無いチャンネルは program 255・volume 0 です。
三つに共通して family_fields が置く値は、master_lim = LIMITER、master_vol = 100、click オフ、拍 4/4、selected = 0、confirm_family = −1。テンポとホールは表から：Rock 128 / 40・40・30・25、Classic 84 / 75・35・55・45、Orchestra 96 / 85・40・60・40（room・damping・feedback・wet の順）。クリックはシーン音量に入りません（bus 65 の専用加算、7.4）。lighting は三つとも空（埋める関数が memset から始める）。accent は Rock と Classic の表にあり、Orchestra の表はゼロ。どのテンプレートも REVERB を置きません — send は同じ一つのホールへ行くからです（第四章 4.3）。
確認の流れ。空でないセッションで一度目を押すと confirm_family だけを置いて何も変えません（ステージの FAMILY ボタンに "?" が付くのはこの状態）。同じ family を二度目いて適用します。セッションが空（track_count と event_count が 0）なら即適用 — orch_cmd_new が確認なしで ROCK を置くのも、起動直後の orch_boot_desk が同じことをするのもこの条です。PLAYING 中の要求は 7.7 の refuse_tempo。
Why a template needs a second press. Applying a template destroys every event in the session, and the undo ring of 7.6 does not cover it — the ring records individual field writes, not a wholesale replacement. So the destructive half is gated by an explicit confirmation held in the session struct, which also survives a window switch, and the label that reads "?" tells the operator which press was just spent. On an empty session the gate is lifted because there is nothing left to destroy.

The length is the first validator. A fixed 73408-byte container means a hostile or truncated file is rejected by stat before one body byte is read, and the static buffer cannot be resized to whatever a field claims. Every ceiling the file carries (64 tracks, 16 scenes, 4096 events, eight slots per algorithm) is a ceiling the running desk already has, so the validator is a restatement rather than a second policy — and because the restatement is generated from the same enum ranges, a new insert type cannot be written to disk before it can be played.
Why no pointers and no structure image. The file is a serialization of a POD desk snapshot, not a memory dump. Compiler alignment is not normative, so writing the struct would make the byte offsets a property of the toolchain; naming each field makes 73408 a property of the format. That is also what keeps version 1 readable on all seven targets, where the C ABI's padding rules differ.

Two different failure disciplines, and the reason for each. Structural damage (bad header, chunk that does not fit, missing terminator) refuses the whole file, because a half-parsed file is not music — it is a partial instrument. Overflow (more events than 4096) does not: the file is well-formed, the desk is simply smaller than the file, so the surplus is counted and dropped. That single distinction is why refuse_smf can be nonzero on a valid load, and why the manual prints it in the status line.
Round-trip is the album's test. The piece that builds the four album files re-reads what it wrote and compares event counts before and after (chapter ten), so SMF is verified by a differential, not by an example. Where the channel assignment needed no splitting, the counts must match exactly — which is the check that catches a lost or duplicated note without needing a listener.

Export borrows the engine, not the state. The exported file must be the same audio the stage would have produced, so it cannot be a second renderer with its own approximations — it calls the same five functions. But it must also leave the desk exactly where it was found, which is why it keeps a private slot table, restores fifteen counters and the transport position, and is the reason the meters freeze rather than flicker through an album take. N is never read or written by the loop; the chase index and the shim's time argument are the export's own local clock, which is why chapter five's measured queue is untouched by an export.

チャンネル 1..8 の八本の Crystal chime がカノンを組みます。入りの位置は 0、960、1440、4320、6720、7200、7200、10080 — 四分音符をおきに三つ、そのあとは小節おき。持つイベントは後にいくほど減って、七番目と八番目は一打ちだけになります。インサートを持つのは 0 番目とマスターバスだけで、ほかの七つの入り口はドライのままです。
チャンネル 9 の Golden chi bell は 0 番目の一打ち（key 44、9408 チック）で、ファイルの最長。10..13 がリズム（Hi-hat 59 を GATE で、kick 20、snare 38、snare 2 の三打ち）。14 がベース（program 32 を EQ と CHORUS へ、鍵 35..52）。15 の三つの長い音（program 80）と 16 の四つの流れ（program 102）は中程から入り、16 枚目は第一の鐘とチャンネル 1 を分けて、46080 チックから尾で三つの音（84..91）だけ鳴らします。
アルゴリズムあたりの枠は第四章の天井（八）より少ない — EQ 六、REVERB 四、GATE 三、DELAY 一、CHORUS 一。四つの REVERB は自分のトラックの send を書き、ホールの摘みは走査の最後に読んだ一台（チャンネル 16）がブロックまで届きます。feedback のバイト 18 はそのまま — インサートは触らないので（9.1）。
One dry channel in a canon is a decision, not an oversight. Only the first entering voice carries EQ and REVERB; the seven later entries are dry. Because the hall is a single shared block (chapter four), a send on every voice would stack the same room eight times and the canon would lose its depth ordering. Dry entries are what let the listener hear which bell is answering.
The last open divergence. The companion document doc/txt/SOUND.txt describes the same piece as "~25.8 seconds (24 Measures)", while the built bells.orch gives 27.36 seconds and 25.5 bars in 3/4. The file is normative — it is what the desk reads — and SOUND.txt describes a scene, not a container. The correction belongs in SOUND.txt, and chapter twelve lists it rather than quietly harmonising the two numbers.
