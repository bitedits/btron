## 1. Загальний огляд екосистеми

B-System — спеціалізована операційна система (на базі TRON/μITRON архітектури) для:
- Радіоаматорів та SDR
- Професійного та напівпрофесійного звуку
- Живих концертів гаражних і клубних груп

Центральний продукт екосистеми — **Orchestra**.  
Навколо нього будуються супутні продукти, які можуть працювати як окремі додатки або як модулі.

### Список продуктів

|--------------------|----------------------|-----------|----------------------------------------------------|
| **Orchestra**      | Основний             | P0        | Live MIDI-сервер + Stage DAW                       |

## 2. Загальні системні вимоги (для всіх продуктів)

### 2.1. Real-time і латентність

- Soft real-time поведінка з пріоритетом аудіо/MIDI потоків.
- Цільова round-trip латентність аудіо: **≤ 5–8 мс** (ідеально < 5 мс).
- MIDI event-to-output latency: **< 0.5 мс** (ціль < 0.2 мс).
- Нульова толерантність до xruns під час live-виступу.
- Детермінований диспетчер задач (μITRON).

### 2.2. Аудіо-стек

- Вбудований або тісно інтегрований media pipeline (GStreamer C99 або власний Media Kit-подібний шар).
- Підтримка sample rates: 44.1 / 48 / 96 кГц (основний — 48 кГц).
- Підтримка bit depth: 16 / 24 / 32-bit float.
- Прямий доступ до апаратури (VirtIO-Sound, class-compliant USB, нативні драйвери).

### 2.3. MIDI

- USB-MIDI, DIN-5, VirtIO-MIDI, Network MIDI (RTP-MIDI).
- Підтримка MIDI 1.0 (обов’язково) + підготовка до MIDI 2.0.
- Віртуальні порти (IAC-подібні).
- Timestamping з наносекундною точністю.

### 2.4. Надійність

- Відсутність модальних діалогів, які блокують UI під час концерту.
- Швидке відновлення після збою.
- Можливість роботи на слабкому залозі (міні-ПК, ноутбуки).
- Статичний footprint основних компонентів — якомога менший.

### 2.5. Інтеграція

- Усі продукти повинні вміти обмінюватися даними через спільну шину повідомлень / IPC B-System.
- Orchestra виступає центральним хабом для MIDI і аудіо-маршрутизації.

## 3. Детальні вимоги до кожного продукту

### 3.1. Orchestra (P0 — Flagship)

Призначення: Головний live MIDI-сервер і stage workstation. Конкурує з GarageBand (зручність) + Pro Tools (надійність) у концертному контексті.

#### Функціональні вимоги (MVP)

**MIDI**
- Прийом з USB / DIN / VirtIO / Network MIDI.
- До 32–64 MIDI-треків.
- Keyboard Split / Layer.
- Velocity curves.
- Program Change / Bank Select (індивідуально і масово по сцені).
- Panic (All Notes Off + Controllers Reset).

**Сцени (Scenes / Snapshots)**
- Мінімум 16 сцен на пісню.
- Миттєве перемикання сцен.
- Збереження стану маршрутизації, Program Change, рівнів тощо.

**Аудіо**
- Вбудований синтез (FluidSynth / SoundFont).
- Main Bus + мінімум 4–8 Aux (Monitor) шин.
- Базова підтримка аудіо-входів (для вокалу / гітари).

**Transport & Sync**
- Play / Stop / Pause.
- MIDI Clock output.
- MTC (базовий рівень).
- Метроном.

**Сесії**
- Збереження / завантаження сетлиста і сесії.
- Підтримка Standard MIDI File (SMF).

**Моніторинг**
- Індикатор латентності, CPU, xruns у реальному часі.

#### Нефункціональні вимоги

- Латентність MIDI < 0.3 мс.
- Стабільна робота 3+ години без збоїв.
- Footprint ядра < 5–10 МБ (ціль < 2 МБ для критичних частин).
- UI оптимізований під сцену (великі кнопки, мінімум дрібного тексту, можливість роботи з MIDI-контролера).

#### Майбутні розширення (Post-MVP)

- Повноцінний плагін-хост (LV2 / VST).
- Багатоканальний запис.
- DMX / освітлення.
- Глибока інтеграція з SDR.
- Dual-machine redundancy.

### 3.2. Tuner / Scope (P0)

Призначення: SDR-приймач і аналізатор спектра для радіоаматорів.

#### Функціональні вимоги (MVP)

- Підтримка основних SDR: RTL-SDR, Airspy, HackRF, SDRplay, PlutoSDR (через SoapySDR або нативні драйвери).
- Spectrum + Waterfall відображення.
- Режими: NFM, WFM, AM, USB, LSB, CW.
- Налаштування частоти, смуги, gain, squelch.
- Аудіо-вихід (можливість направити в Orchestra або системний вихід).
- Базовий запис IQ / аудіо.

#### Нефункціональні

- Плавне оновлення спектра (30+ FPS бажано).
- Низьке навантаження на CPU.
- Можливість роботи паралельно з Orchestra.

### 3.3. Logger (P0)

Призначення: Класичний QSO-лог для радіоаматорів.

#### Функціональні вимоги (MVP)

- Додавання / редагування / видалення QSO.
- Поля: час, позивний, частота, режим, RST, ім’я, замітки.
- Фільтрація і пошук.
- Експорт у ADIF.
- Базова інтеграція з Tuner (автозаповнення частоти / режиму).

#### Нефункціональні

- Швидкий і простий інтерфейс.
- Надійне збереження даних (навіть при збої живлення).

### 3.4. Click & Cue (P1)

Призначення: Надійний метроном + система cues для групи.

#### Функціональні вимоги (MVP)

- Точний метроном з налаштуванням BPM і time signature.
- Tap tempo.
- Список cues (Intro, Verse, Chorus, Solo тощо).
- Можливість призначати cues на MIDI-кнопки / сцени Orchestra.
- Окремий аудіо-вихід (можна направити тільки барабанщику).

#### Нефункціональні

- Абсолютна стабільність timing.
- Мінімальний UI, щоб не відволікати.

### 3.5. Router (P1)

Призначення: Візуальний конструктор маршрутизації MIDI та аудіо.

#### Функціональні вимоги (MVP)

- Список усіх доступних MIDI in/out портів.
- Можливість створювати маршрути (з фільтрацією каналів).
- Базові аудіо-шини (Main + Aux).
- Збереження пресетів маршрутизації.
- Інтеграція з Orchestra (Orchestra може використовувати Router як backend).

#### Нефункціональні

- Наочний графічний інтерфейс (блоки + лінії).
- Зміни маршрутизації застосовуються миттєво і без клацань.

### 3.6. Recorder (P1)

Призначення: Запис концерту (стеми + стерео).

#### Функціональні вимоги (MVP)

- Запис Main Bus (стерео).
- Запис окремих Aux / Group шин (стеми).
- Arm / Disarm треків.
- Відображення рівнів у реальному часі.
- Формат: WAV 48 кГц / 24-bit (мінімум).
- Автоматичне створення папки по даті концерту.

#### Нефункціональні

- Запис не повинен впливати на латентність playback.
- Надійний запис навіть при високому навантаженні.

### 3.7. Monitor (P1)

Призначення: Системна діагностика в реальному часі.

#### Функціональні вимоги (MVP)

- Показ поточної латентності.
- Лічильник xruns.
- Навантаження CPU (окремо audio thread).
- Список активних MIDI і аудіо портів.
- Можливість скинути статистику.
- Опціонально — лог подій.

#### Нефункціональні

- Дуже легкий (майже нульове навантаження).
- Завжди поверх інших вікон або в окремому маленькому вікні.

### 3.8. Scene Manager (P2 — опціонально)

Призначення: Легкий окремий інструмент для швидкого перемикання сцен, якщо Orchestra запущена в мінімальному режимі.

#### Функціональні вимоги

- Список сцен поточної пісні.
- Швидкий Recall.
- Призначення на MIDI-кнопки.
- Синхронізація з Orchestra.

## 4. Пріоритети розробки (Roadmap)

### Фаза 1 — MVP (мінімально життєздатний концертний сетап)

1. Orchestra (ядро + сцени + базові шини + FluidSynth)
2. Tuner / Scope (базовий)
3. Logger (базовий)
4. Monitor (базовий)

### Фаза 2 — Повноцінний live

5. Click & Cue
6. Router
7. Recorder
8. Покращення шин і моніторингу в Orchestra

### Фаза 3 — Розширення

- Глибока SDR ↔ Orchestra інтеграція
- Network redundancy
- Плагін-хост
- DMX / освітлення
- MIDI 2.0

## 5. Критерії приймання (Definition of Done)

Продукт вважається готовим до MVP, якщо:

- Працює стабільно ≥ 3 години під навантаженням, близьким до реального концерту.
- Немає xruns при цільовій латентності.
- UI дозволяє виконати основні дії під час виступу без миші (або з мінімумом миші).
- Є документація по основних сценаріях використання.
- Інтегрується з іншими продуктами екосистеми через стандартні механізми B-System.

## 6. Примітки для розробників

- Усі критичні аудіо/MIDI шляхи повинні бути zero-allocation у hot path (де можливо).
- Уникати блокуючих системних викликів у real-time потоках.
- Логування — тільки асинхронне.
- Тестувати на реальному залізі (USB-аудіоінтерфейси + MIDI-клавіатури + SDR-донглі).
