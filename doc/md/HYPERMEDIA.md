# HYPERMEDIA.md

**Опис**: Стратегічний фокус B-System (BTRON 3.20 Alpha 1 «Ceremony»). Єдина пріоритетна мета: бездоганна інтерактивна демонстрація Real Body / Virtual Body (実身／仮身) гіпермедіа-моделі.
**Дата:** 10 вересня 2026

## 1. Стратегічне обґрунтування фокусування

### 1.1. Поточний стан

B-System вже має:

- Повноцінну cleanroom-реалізацію vobj-двигуна (Real Body / Virtual Body).
- HFDS-кабінети, TAD-браузер, Object Explorer.
- Багатоцільову підтримку (POSIX/SDL2, QEMU VirtIO, Raspberry Pi, UEFI, PC-98, MIPS, PS2 тощо).
- 15+ додатків і високу формальну відповідність специфікації.

Проте система залишається «музейною» для зовнішнього спостерігача: немає жодного **одного** сценарію
 який би змусив людину (особливо японського дослідника TRON/BTRON) сказати: «Ось воно — те саме, що
 Sakamura описував у 1980-х, і воно працює **живим**».

### 1.2. Чому саме цей фокус дає максимальний важіль

- **Унікальна цінність BTRON** — не мікроядро, не VirtIO і не кількість архітектур. Унікальна цінність — **гіпермедіа-модель 実身／仮身**, де дані живуть як графи об’єктів із живими вкладеннями, а не як дерева файлів.
- Один ідеальний демо-сценарій вартий десяти нових платформ у плані залучення спільноти, довіри японських дослідників і появи перших зовнішніх контриб’юторів.
- Alpha-стадія + соло-розробка = критична потреба в **фокусі**, а не в розширенні поверхні.

### 1.3. Критерій успіху (один речення)

Користувач (японець або західний ентузіаст) за 3–5 хвилин після `make run-posix` може створити, відредагувати, зберегти і повторно відкрити документ, у якому живуть вкладені реальні об’єкти (текст + малюнок + інший документ + посилання), і зрозуміти, що це **не** гіперпосилання Unix/Windows, а справжня модель Real/Virtual Body.

## 2. Концепція демо («Hypermedia Ceremony»)

### 2.1. Назва і метафора

**«Hypermedia Ceremony»** — ритуальне створення живого гіпердокумента, яке демонструє сутність BTRON.

### 2.2. Сценарій користувача (ідеальний шлях 3–7 хвилин)

1. Запуск системи (`make run-posix` або `make run-qemu`).
2. На столі з’являється один кабінет «デモ」 з готовим Real Body «Ceremony Document».
3. Подвійний клік → відкривається T-Editor / TAD-браузер.
4. Користувач бачить текст японською + англійською, у якому вже є:
   - Virtual Body → інший документ (вкладений Real Body).
   - Virtual Body → малюнок (або простий vector figure).
   - Virtual Body → невеликий виконуваний запис (або просто посилання на інший Real Body).
5. Користувач може:
   - Редагувати текст.
   - Подвійним кліком «зануритися» у вкладений об’єкт.
   - Створити новий Real Body і вставити його як Virtual Body у поточний документ.
   - Зберегти зміни (персистентність через VirtIO-Block / локальний кабінет).
   - Закрити і знову відкрити — зміни збережені, граф об’єктів живий.
6. Додатковий «wow-момент»: можливість мати один і той самий Real Body, на який посилаються кілька Virtual Body в різних документах (справжнє спільне використання даних, а не копії).

### 2.3. Технічні вимоги до демо

- Повна персистентність (запис/читання Real Body через HFDS).
- Живе редагування вкладених об’єктів без перезавантаження системи.
- Візуальна індикація Virtual Body (іконка, рамка, курсор «link»).
- Історія навігації (вперед/назад по графу).
- Мінімум «магії» — все має бути зрозуміло з UI, без консольних команд.
- Стабільна робота саме на **одній** цілі: POSIX/SDL2 (найшвидший цикл розробки) + QEMU VirtIO як друга ціль для «реалістичності».

### 2.4. Що **не** входить у цей фокус

- Нові апаратні платформи.
- Додаткові мови/IME поза вже наявними.
- Нові додатки (окрім мінімальних покращень існуючих для підтримки демо).
- Формальна верифікація всього ядра.
- Покращення conformance вище 90% (достатньо для демо).

## 3. Детальний план реалізації (4 фази)

### Фаза 0. Аудит і фіксація бази

- Повністю задокументувати поточний стан `vobj.c`, HFDS, TAD, Object Explorer і T-Editor.
- Визначити, які частини вже працюють стабільно, а які «майже».
- Заморозити всі інші напрямки розвитку (нові targets, нові apps).
- Створити гілку `hypermedia-demo` або milestone.

**Результат:** чіткий список gaps між «є реалізація» і «є переконливе демо».

### Фаза 1. Стабілізація ядра гіпермедіа

Пріоритети:

1. Надійне створення / відкриття / збереження Real Body.
2. Коректне вставлення / розв’язання Virtual Body (посилання не ламаються після перезапуску).
3. Редагування вкладеного об’єкта «на місці» або через занурення з поверненням.
4. Візуальне розрізнення Real vs Virtual Body в UI (іконки, підсвітка, курсор).
5. Проста історія навігації (stack).

Мінімальні зміни в існуючих додатках (T-Editor, Object Explorer, TAD Browser).
Жодних нових великих підсистем.

**Критерій готовності фази:** можна вручну створити документ з 2–3 рівнями вкладення, зберегти, перезапустити систему і побачити той самий граф.

### Фаза 2. Поліровка UX і створення «Ceremony Document»

- Підготувати готовий стартовий Real Body «Ceremony» (японською + англійською).
- Зробити шлях запуску максимально коротким (`make run-posix` → одразу видно демо).
- Додати підказки / коротку довідку всередині самого документа (self-documenting).
- Прибрати будь-які крэші, зависання, втрату даних у сценарії демо.
- Зробити відео-запис ідеального проходження (1–2 хвилини).

**Критерій:** сторонній розробник може пройти сценарій без інструкцій і без «магії».

### Фаза 3. Документація, упаковка і комунікація

- Окремий розділ у `README` / на сайті: «Hypermedia Demo — Start Here».
- Короткий гайд (українською + англійською + японською).
- Оновити `releases.html` і головну сторінку з акцентом на гіпермедіа, а не на кількість платформ.
- Підготувати повідомлення для японської спільноти TRON/BTRON (Twitter/X, форуми, листи до дослідників).

### Фаза 4. Збір зворотного зв’язку і ітерація (безстроково, але з жорстким пріоритетом)

- Вимірювати: чи люди реально запускають демо і залишають відгуки.
- Фіксувати баги **тільки** ті, що ламають сценарій Ceremony.
- Не розширювати scope, поки демо не стане «бездоганним» у відчутті користувача.

## 4. Стратегія досягнення результатів

### 4.1. Метрики успіху (вимірювані)

| Метрика                        | Ціль (через 3–4 тижні)      |
|--------------------------------|-----------------------------|
| Час від клону до живого демо   | ≤ 60 секунд                 |
| Сценарій Ceremony проходиться  | 100% без помилок            |

### 4.2. Комунікаційна стратегія

1. **Внутрішня дисципліна:** кожен коміт у гілці фокусу має відповідати на питання «чи це робить Ceremony-демо кращим?».

2. **Зовнішнє позиціонування:** перестати продавати «7 платформ і 90% conformance». Почати продавати «живе втілення 実身／仮身 моделі 2026 року».

3. **Цільова аудиторія першого кола:**
   - Японські дослідники і ентузіасти TRON/BTRON/Cho-Kanji.
   - Академічні групи, що викладають ОС і гіпермедіа.
   - Люди, які пам’ятають BeOS / HyperCard / NoteCards і розуміють цінність цієї моделі даних для компактних систем документообігу.

4. **Канали:**
   - Оновлення головної сторінки + releases.
   - Прямі звернення до відомих людей з TRON-спільноти.
   - Пост у форматі «що саме відрізняє Real/Virtual Body від звичайних гіперпосилань».

### 4.3. Технічна дисципліна

- Один primary target для щоденної розробки: `make run-posix`.
- Другий target для валідації: `make run-qemu`.
- Усі інші targets — freeze до моменту, коли Ceremony стане бездоганним.
- Кожен новий коміт має проходити мінімальний smoke-тест сценарію демо.

## 5. Вимоги до реалізації (чек-лист)

### Обов’язкові (Must)

- [ ] Стабільне створення, збереження і завантаження Real Body.
- [ ] Коректна робота Virtual Body (посилання не ламаються після reboot).
- [ ] Живе редагування тексту всередині документа.
- [ ] Можливість вставити новий Virtual Body у існуючий документ.
- [ ] Візуальна відмінність Virtual Body від звичайного тексту/об’єкта.
- [ ] Готовий стартовий документ «Ceremony» з вкладеннями.
- [ ] Шлях запуску ≤ 1 команда + кілька кліків.
- [ ] Персистентність даних між запусками.
- [ ] Відсутність крэшів у сценарії демо.

### Бажані (Should)

- [ ] Історія навігації по графу (Back/Forward).
- [ ] Один Real Body, на який посилаються кілька Virtual Body.
- [ ] Мінімальна довідка всередині самого документа.
- [ ] Відео-запис ідеального проходження.
- [ ] Англійська + японська версія тексту Ceremony.

### Можна відкласти (Could)

- [ ] Редагування векторної графіки «на місці».
- [ ] Виконувані записи всередині Real Body.
- [ ] Спільне редагування кількома процесами.
- [ ] Повна формальна верифікація vobj-двигуна.

## 6. Філософія фокусу (для автора)

Ми вже зробили багато: за два тижні підняли cleanroom BTRON3 з нуля до Alpha з 7 цілями і 90% conformance.
Тепер найцінніше, що можна зробити — **не додати ще одну ціль**, а зробити так, щоб єдина справді унікальна ідея BTRON (実身／仮身) засяяла так яскраво, щоб її неможливо було проігнорувати. Один бездоганний живий демо-сценарій вартує більше, ніж ще десять архітектур. Це і є наступна «Ceremony».

*Цей документ є обов’язковим стратегічним артефактом. Усі рішення щодо пріоритетів розробки B-System у найближчі тижні мають перевірятися питанням: «Чи робить це Hypermedia Ceremony кращим?»*
