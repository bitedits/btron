0. Problem Statement & Research Thesis
--------------------------------------

Hypermedia scripting in historical BTRON—principally MicroScript (also known as
Programming-Language-T in Personal Media Corp / Chokanji documentation)—provides
an interactive, card- and figure-based execution surface. Historically, scripting
interpreters in consumer and desktop systems have relied on ad-hoc, untyped byte-
code engines, unbounded garbage-collected heaps, dynamic memory allocation, and
ad-hoc cooperative or preemptive threading with global interpreter locks (GIL).

Such execution models are fundamentally incompatible with soft- and hard-real-time
kernel certification:
  1. Unbounded dynamic allocation breaks memory predictability and violates
     the NASA JPL "Power of 10" safety-critical coding discipline.
  2. Locking, mutexes, and thread synchronization introduce priority inversion,
     convoying, and deadlocks between real-time input planes and UI tasks.
  3. Ad-hoc script semantics lack a formal mathematical standard against which
     an implementation can claim conformance.
  4. Memory buffer copies (memcpy) across process/actor boundaries create non-deterministic
     latency spikes and cache thrashing that degrade sub-millisecond audio/GUI responsiveness.

Thesis:
  A verified interpreter for BTRON is NOT a language compiler or an imperative
  stack machine. It is a TOTAL STATE TRANSFORMER (S -> S * R) operating over the
  formal InterCore bus, whose operational semantics strictly refine published
  international formal standards:
    - ITU-T Z.100 / Z.101 (SDL-2010) Annex F for the process/agent and signal queueing model;
    - ISO/IEC 15437 (E-LOTOS) for the commutation lemma and trace equivalence;
    - ISO/IEC 15909 (High-Level Petri Nets) for the watermark token conservation invariants;
    - Calculus of Inductive Constructions (CIC) as the sole mechanical proof kernel.

  Target Baseline — "Like Verified Erlang (Not Worse Than)":
    The Verifiable Interpreter must be AT LEAST AS RIGOROUS AS A VERIFIED ERLANG
    (and in key real-time dimensions, strictly superior). It realizes the Erlang/OTP
    actor ideal—shared-nothing memory, discrete message mailboxes, reduction-based
    preemptive execution budgets, and isolated fault boundaries—while eliminating
    Erlang's historical weaknesses for hard real-time systems (unbounded mailbox
    accumulation, unpredictable garbage collection pauses, and dynamic heap growth).


1. Standards Conformance Landscape: Why Standards, Not Languages
----------------------------------------------------------------

The primary architectural decision is to conform to published, ratified international
concurrency standards rather than specific programming language specifications.

1.1 Failure of Language Standards for Real-Time IPC
  - ISO/IEC 9899 (C) and ISO/IEC 14882 (C++):
    C provides no formal memory or concurrency semantics outside of atomic primitives
    and pthreads. Concurrency is delegated to the platform.
  - ISO/IEC 9945 (POSIX):
    POSIX defines the shell and multi-threaded UNIX environment (pthreads, mutexes,
    condition variables, signals). POSIX describes a time-shared workstation model,
    not a deterministic real-time actor machine. Mutexes explicitly permit priority
    inversion.
  - IETF RFCs:
    The IETF specifies wire formats, transport protocols (RTP, TCP, UDP), and syntax.
    It does not define execution semantics, operational transitions, or interpreter
    conformance.

1.2 ITU-T Z.100 / Z.101 (SDL-2010): The Reference Architecture for Agents
  ITU-T Recommendation Z.100 (Specification and Description Language - SDL-2010) and
  Z.101 (Basic SDL-2010) provide the only internationally ratified formal standard whose
  conceptual user model matches BTRON hypermedia actors and the InterCore calculus:
    - An AGENT is a concurrent PROCESS.
    - COMMUNICATION is via discrete SIGNALS, output by one agent and input by another.
    - Each process owns exactly ONE INPUT PORT, where incoming signals are queued.
    - A process can dynamically CREATE (SPAWN) another process.
    - Conformance is defined against abstract grammars (AS0 -> AS1 -> AS2), NOT against
      a compiler binary or machine byte-code.
    - Annex F (Z.100 Annex F.1-F.3, 2021 edition) provides the formal definition:
      static semantics (well-formedness rules) and dynamic semantics formalized as
      an Abstract State Machine (ASM) whose underlying message exchange is CSP-shaped.

  Under BTRON, the concrete syntax of MicroScript is an AS0/AS1 surface that lowers
  into Z.101 AS2 agents and signals. The meta-model in Annex F maps directly onto the
  five InterCore primitives:
      SDL Operation     InterCore Equivalent    Formal Semantics
      -------------------------------------------------------------------
      create            spawn                   Table slot allocation & cursor grant
      output            snd                     Append to bounded ring or refuse (drop)
      input             rcv                     Advance reader cursor or report empty
      inputPort         w_hist / reader         Single-consumer projection over sector
      stop              terminate / exit        Slot reclamation and cursor revoke

1.3 ISO/IEC 15437 (E-LOTOS): Commutation & Trace Equivalence
  ISO/IEC 15437 (Enhanced LOTOS) defines an algebraic, timed process calculus with
  operational semantics based on labeled transition systems (LTS).
  While E-LOTOS is a specification language without dedicated input queues, it provides
  the mathematical foundation for:
    - The Commutation Lemma: two non-interfering agent steps operating on disjoint
      coordinates of the bus commute definitionally:
        δ(a) ∘ δ(b) = δ(b) ∘ δ(a)
    - Mazurkiewicz Trace Monoids: the quotient of execution traces under the commutation
      relation permits partial-order reduction. Proofs about all possible interleavings
      reduce equationally to proofs about independent local executions.

1.4 ISO/IEC 15909 (High-Level Petri Nets): Marking & Conservation Laws
  ISO/IEC 15909 defines High-Level Petri Nets (HLPN). It matches the watermark arithmetic
  and capacity tracking of the BTRON InterCore sector pool:
    - Items (signals, sectors, messages) and queue capacities correspond to tokens and
      place capacities.
    - Universal Conservation Law:
        n_in = n_out + n_held + n_lost
    - Pool Invariant:
        total_held(b) + pool_free(b) = sector_pool
    ISO/IEC 15909 provides the formal standard for modeling the resource invariant,
    ensuring that no signal or memory token is created or destroyed without accounting.

1.4.1 ISO/IEC 19510 (BPMN 2.0) vs ISO/IEC 15909: Layer Separation Analysis
  An architectural question arises whether ISO/IEC 19510 (Business Process Model
  and Notation - BPMN 2.0) could replace ISO/IEC 15909 (High-Level Petri Nets) as
  a "better alternative" for MicroScript and the BTRON interpreter:

  1. Layer B (Verifiable Kernel & Bus Conservation): Petri Nets Win Decisively
     - Mathematical Foundation: ISO/IEC 15909 is grounded in linear algebra. Places,
       transitions, incidence matrices C, and marking state equations M_k = M_0 + C * σ
       provide exact, closed algebraic invariants. Place invariants (P-invariants, where
       C^T * y = 0) yield immediate, axiom-free proofs in Rocq/Coq using `lia`/`ring`.
     - ISO/IEC 19510 Deficiencies at Layer B: BPMN 2.0 is an informal, 500+ page OMG/ISO
       metamodel without native closed-form state equations. In formal methods literature,
       BPMN execution semantics are notoriously ambiguous; verifying BPMN workflows
       traditionally requires *compiling them into Petri nets* (Workflow Nets / YAWL).
     - Semantic Domain Mismatch: BPMN 2.0 is built for enterprise workflows (human tasks,
       compensation events, inclusive OR-joins, web-service choreographies). Attempting
       to model hardware-adjacent lock-free SPSC rings or InterCore sector pools using
       BPMN introduces severe impedance mismatch.

  2. Layer A (Hypermedia Choreography & Scene Flow): BPMN 2.0 is Superior
     - MicroScript hypermedia authoring operates over visual cards, scenes, dialogs,
       figure triggers, and user interaction sequences.
     - At this human-facing scenario level (Layer A), BPMN 2.0 provides an internationally
       standardized, visually intuitive workflow notation:
         * BPMN Pools & Lanes    -> MicroScript Tasks & Agents
         * BPMN Sequence Flow    -> Hypermedia Card/Scene Transitions (SCENE, CARD)
         * BPMN Gateways (XOR)   -> Conditional Scene Branches (IF, CASE)
         * BPMN Signal Events    -> ITU-T Z.101 AS2 Signals (SIGNAL, SEND, RECEIVE)
     - Architectural Verdict: Retain ISO/IEC 15909 at Layer B for mechanical proof
       of watermark and memory conservation; adopt ISO/IEC 19510 optionally at Layer A
       as a visual hypermedia authoring metamodel that compiles down into Z.101 AS2 agents
       and ISO 15909 token nets.

3.0 InterCore Protocol: The Universal System Nexus (Heart of BTRON)
  The InterCore protocol (originating in platform.rs / o83 lineage) is not merely a
  specialized message transport for MicroScript; it is the NORMATIVE HEART of the
  entire BTRON operating system. It unifies all system planes into a single,
  coherent, mathematically verified concurrency fabric:

    1. Hardware & IRQ Plane (Tier 1):
       xHCI, timer, keyboard/mouse ISRs do not invoke GUI or allocator functions;
       they obtain a publisher cursor via `pub` and non-blockingly emit raw event
       snapshots into the bus with `snd`.
    2. Real-Time Media & Streaming Plane:
       NuStream audio/video engines (doc/txt/ASYNC.txt, media_smp/rtp models) utilize
       InterCore CAS multicursor ring sectors for zero-copy frame pipeline routing.
    3. Windowing & Presentation Plane:
       Clarity frames, Cabinet drag-and-drop, and TAD display engines drain input
       events through InterCore `rcv` reader cursors under strict frame time budgets.
    4. Hypermedia Scripting Plane (MicroScript / Language T):
       High-level user agents and BPMN/Z.101 workflows compile down to identical
       InterCore `pub`/`sub`/`spawn`/`snd`/`rcv` primitives.

  By establishing the InterCore protocol as the immutable heart of BTRON:
    - The Mutex-Elimination Theorem applies uniformly from ISR to user script:
      no locks, no mutexes, and zero priority inversion across cores.
    - Watermark Token Conservation (ISO/IEC 15909) accounts for every sector,
      signal, and packet without leak or unbounded accumulation.
    - Total state transformations guarantee deterministic, soft- and hard-real-time
      predictability across the symmetric multi-core architecture.

In standard ITU-T Z.100, an agent's input port is an unbounded FIFO queue. In a certified
real-time OS, unbounded queues are strictly forbidden. The BTRON architecture realizes
Z.101 input ports over the InterCore lock-free star topology.

3.1 The InterCore Star Topology
  Instead of an MPSC broker or central lock, each core owns its own writer ring:

     Core 0 (Writer 0) ---\
     Core 1 (Writer 1) ----+---> [ MPSC Derived Projection M ] ---> Agent Input Port
     Core 2 (Writer 2) ----+
     Core 3 (Writer 3) ---/

  MPSC(bus) ≜ λ rid. hist_{wid(rid)} [ cur_{rid} ]

  Broker-freeness: The multi-consumer view is a pure functional projection over the
  producer histories. There is no central queue, no spinlock, and no kernel trap.

3.2 Bounded Port Refusal & Drop Accounting
  When agent A outputs a signal to agent B:
    - If the destination ring has room:
        snd(wid, signal) -> (bus', S_OK)
    - If the destination ring is full:
        snd(wid, signal) -> (bus', S_FULL(drop_count))
      The signal is dropped, the writer's drop counter is incremented, and the caller
      receives a receipt indicating refusal. The sender never blocks.
    - When an agent polls its input port:
        rcv(rid) -> (bus', R_DATA(val))   if signal available
        rcv(rid) -> (bus', R_EMPTY)       if port empty
      The receiver never blocks. Soft real-time determinism is preserved.

3.3 Zero-Copy Frontier Transfer & Sector Pool Invariant
  To satisfy the NASA JPL Power of 10 discipline (Rule 3: zero heap allocation after init)
  and 1 ms audio/GUI deadlines, the Verifiable Interpreter mandates a strict
  ZERO-COPY invariant across all actor communication:

  1. In-Place Sector Allocation:
     When an agent constructs a signal with a large payload (e.g. TAD segment, figure vector,
     or text buffer), it acquires an immutable sector index `sec_id` from the pre-allocated
     InterCore sector pool (`b_pool_free`). Data is written in-place directly into the sector.

  2. Token Index Transfer (Zero Memcpy):
     The signal `sig_val` transmitted via `snd(wid, sig)` carries the scalar `sec_id` token index.
     Zero bytes of payload memory are copied across cores or queue buffers.

  3. Single-Consumer Exclusive Ownership:
     By the Mutex-Elimination Theorem, only the current cursor holder has read access to the
     sector. When the receiver consumes the signal via `rcv(rid)`, ownership of the sector token
     passes to the receiving agent.

  4. Mass Balance Conservation (ISO/IEC 15909):
     Every allocated sector token must be returned to `b_pool_free` upon processing, satisfying
     the universal conservation law:
       total_held(b) + pool_free(b) = sector_pool


4. Formal Calculus in CIC: State & Step Signatures
--------------------------------------------------

4.1 Bus and Agent State Formulation
  The system state S is a tuple of total functions over dense small natural numbers:

    Record agent : Type := mk_agent {
        a_live  : bool;
        a_core  : nat;
        a_pc    : nat;
        a_state : nat;
        a_wid   : nat;              (* Input Port writer ID *)
        a_rid   : nat;              (* Input Port reader ID *)
        a_vars  : nat -> nat;       (* Bounded variable store *)
        a_fuel  : nat               (* Execution step fuel *)
    }.

    Record bus : Type := mk_bus {
        b_cores : nat;
        b_w     : nat -> writer;    (* Writer rings *)
        b_r     : nat -> reader;    (* Reader cursors *)
        b_t     : nat -> task;      (* OS tasks *)
        b_a     : nat -> agent      (* MicroScript agents *)
    }.

4.2 Total State Transformer
  Every agent execution step is an inhabitant of:
    Definition agent_step (b : bus) (aid : nat) : bus * step_result

  Receipts returned by agent_step:
    Inductive step_result : Type :=
      | STEP_OK       : step_result
      | STEP_IDLE     : step_result
      | STEP_SEND_OK  : nat -> step_result
      | STEP_SEND_DROP: nat -> step_result
      | STEP_RECV_OK  : nat -> step_result
      | STEP_RECV_NONE: step_result
      | STEP_SPAWN_OK : nat -> step_result
      | STEP_HALT     : step_result.

  Because agent_step is a total function:
    1. It evaluates in finite time (guaranteed termination).
    2. Out-of-bounds indices, full queues, and empty queues produce receipt values
