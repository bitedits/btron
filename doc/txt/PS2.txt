0. How a claim is stated in this book
-------------------------------------

  Every normative statement in this architecture manual conforms strictly
  to four structural components. A statement lacking any of these four
  is treated not as an operational law, but merely as an unverified design
  intention:

  - LAW         The invariant condition that must hold across all execution
                paths, expressed in unambiguous indicative or imperative form.
  - WHY         The precise silicon mechanism, bus topology constraint,
                or pipeline dependency that causes an alternative design
                to fail on real PlayStation 2 hardware.
  - MEASURE     The definitive observable instrument: a hardware performance
                register, ring counter, telemetry telemetry row, or bus cycle
                metric confirming that the invariant holds.
  - GATE        The automated regression check that triggers an immediate
                diagnostic halt if the invariant is violated.

  The book enforces three universal reading and operational principles:

  R1: A zero in a timing column indicates an uninstrumented stub or host-side
      mock, never free silicon work. Real hardware operations on the Emotion
      Engine, Vector Units, and Graphics Synthesizer always incur finite bus
      latencies and execution cycles.
  R2: Architectural quantities carry explicit provenance:
      - PROVEN: Validated through hardware cycle counters, DMA packet traces,
        and reproducible verification gates on bare-metal or cycle-accurate
        emulation (PCSX2).
      - INFERRED: Derived from silicon register specifications, official Sony
        hardware documentation (ps2tek), or architectural analyses.
  R3: Measurement overhead must never contaminate production performance.
      Instrumentation dials (such as floating-point counting or packet
      census) introduce significant CPU overhead and must be decoupled from
      production cycle measurements.

  Prose adheres strictly to a 78-column measure. Architectural tables,
  memory maps, and packet layouts preserve column alignment and do not exceed
  80 columns.


1. The thesis: one agent per parallel component
-----------------------------------------------

1.1  The InterCore Nexus Substrate

  The BTRON B-System 3.20 port to the PlayStation 2 is founded upon the
  InterCore Nexus (defined in doc/txt/ASYNC.txt and doc/txt/INTERPRETER.txt).
  The InterCore Nexus provides an asynchronous, lock-free message-passing
  fabric governed by five fundamental primitives:

    pub [capacity]                  Create a single-producer ring buffer;
                                    yields a system-wide identifier.
    sub [publisher]                 Bind a reader cursor to an existing ring.
    spawn [core; program; cursors]  Instantiate an isolated execution task
                                    with dedicated cursor ownership.
    snd [writer; data]              Non-blocking asynchronous write.
    rcv [reader]                    Non-blocking asynchronous read.

  Scheduling is driven by poll_bus, invoked at every cooperative or timer
  yield. A message delivered across the bus is processed before the
  target engine's next unit of work commences.

  The InterCore topology forms a star network of single-producer,
  single-consumer (SPSC) ring buffers. There is no central broker, no
  global lock, no kernel trap, and no dynamic heap allocation on the
  critical path. This eliminates priority inversion across independent
  execution planes.

  System safety is governed by the Non-Blocking Refusal Law:
    snd on a full ring    -> S_FULL(drop_count)   Sender never stalls.
    rcv on an empty port  -> R_EMPTY              Receiver never blocks.

  Under overload, queues drop or summarize frames gracefully rather than
  stalling the producing core. Workload is partitioned into four distinct
  operating planes:
    Plane 1: Hardware, Interrupts, and Human Interface Devices (HID).
    Plane 2: Real-Time Media Streaming, Synthesis, and Audio (SPU2).
    Plane 3: Windowing, 2D/3D GUI Composition, and Presentation (GS).
    Plane 4: Hypermedia Scripting, Applications, and Shell Interaction.

1.2  Law 1: One Agent Per Parallel Component

  Standard symmetric operating systems treat multicore processors as uniform
  pools of identical execution threads. The PlayStation 2 is fundamentally
  asymmetric: it comprises a single 128-bit MIPS CPU core coupled to five
  autonomous coprocessors and peripheral engines sharing a common memory bus.

  LAW 1 (One Agent per Parallel Component).
  On the PlayStation 2 architecture, every autonomous programmable hardware
  engine shall correspond directly to one InterCore Nexus agent possessing
  its own dedicated SPSC ring buffer, period, and cycle budget.

  WHY: If a hardware coprocessor lacks a dedicated agent, the operating
  system cannot schedule work to it asynchronously. Consequently, its
  workload is implicitly reassigned to the main CPU (the Emotion Engine core).
  When the EE core synchronously executes geometry transformation, raster
  packet formatting, and audio mixing, its execution budget is exhausted,
  inducing severe pipeline stalls and missing the 60 Hz display deadline.

1.3  The Six-Agent Architecture Topology

                               Timer0 + INTC
                            Plane 1: 1 kHz, 50 us
                                    |
                        snd(HID)    |    snd(Commands)
                                    v
     OHCI USB / SIO2 ----> +--------------------+ <---- Graphics Synthesizer
     Plane 1: Input        |    RDRAM 32 MB     |       Plane 3: Rasterizer
                           |    eDRAM  4 MB     |       48 GB/s Bus
     DMAC ch2 -> GIF ----> |    Shared Bus,     | <---- Vector Unit 1 (VU1)
     Plane 3: GIF Ring     |    No Locks        |       Plane 3: Geometry
                           +--------------------+
     IOP / SIF RPC ....... Plane 1/2: Subsystem  ...... SPU2 Audio (Plane 2)

  Emotion Engine (EE R5900): Primary coordinator executing Planes 3 and 4.
  Vector Unit 0 (VU0): Physics, spline evaluation, kinematic agent.
  Vector Unit 1 (VU1): 3D geometry transformation and clipping agent.
  Graphics Synthesizer (GS): Fixed-function rasterization and eDRAM engine.
  Input/Output Processor (IOP): Storage, USB HID, and gamepad driver agent.
  Sound Processing Unit 2 (SPU2): 48-channel hardware audio voice generator.


2. The machine, as six agents on one bus
---------------------------------------

2.1  Hardware Breakdown and Subsystem Maps (ps2tek Architecture)

  The PlayStation 2 console integrates several distinct compute elements:

  1. Emotion Engine (EE Core):
     - CPU: MIPS III R5900 64-bit/128-bit superscalar RISC running at
       294.912 MHz.
     - Registers: 32 general-purpose 128-bit registers (GPRs).
     - Instruction Set: MIPS III with Sony 128-bit Multimedia Extensions
       (MMI: SIMD integer dual-64-bit and quad-32-bit arithmetic).
     - Instruction Cache: 16 KB 2-way set associative (64-byte line size).
     - Data Cache: 8 KB 2-way set associative (64-byte line size),
       write-back with write-allocate.
     - Scratchpad RAM (SPRAM): 16 KB of ultra-fast static RAM mapped to
       virtual address 0x70000000. Provides single-cycle local access for
       DMA packet assembly without cache line eviction.
     - Coprocessor 0 (COP0): System control, TLB, status, exception vectors.
     - Coprocessor 1 (COP1): IEEE single-precision floating-point unit (FPU),
       supporting scalar multiply-add (madd.s, msub.s) at 242 MFLOPS.

  2. Vector Units (VU0 and VU1):
     - VLIW SIMD processors with 32x128-bit vector registers (vf00-vf31) and
       16x16-bit integer registers (vi00-vi15). Each vector register holds
       four 32-bit floats (X, Y, Z, W).
     - VU0: 4 KB microcode RAM, 4 KB data RAM. Located on the EE core bus.
       Operates in Macro Mode (direct COP2 instructions executed by the EE)
       or Micro Mode (independent VLIW execution via VIF0 DMA).
     - VU1: 16 KB microcode RAM, 16 KB data RAM. Autonomous geometry engine
       directly connected to the GS via GIF Path 1 and to EE via VIF1 DMA.
       Peak throughput: 66 million transformed polygons per second.

  3. Graphics Synthesizer (GS):
     - Custom rasterizer running at 147.456 MHz.
     - Embedded DRAM (eDRAM): 4 MB high-density on-chip memory connected
       via an internal 2560-bit bus (1024-bit write, 1024-bit read, 512-bit
       texture read), yielding 48.0 GB/s internal memory bandwidth.
     - Pixel Pipelines: 16 parallel rasterization engines capable of writing
       16 pixels per clock cycle (2.36 GPixels/sec fill rate without texture,
       1.18 GPixels/sec textured).
     - Hardware capabilities: Alpha blending, Z-buffer test, scissor test,
       dithering, fogging, bilinear/trilinear texture filtering, Gouraud
       shading, and antialiasing.
     - Programmable CRT Controller (PCRTC): Generates standard NTSC, PAL,
       DTV (480p), or VESA video timings directly from eDRAM framebuffers.

  4. Direct Memory Access Controller (DMAC):
     - 10 dedicated channels on the EE:
         ch0: VIF0 (EE -> VU0)            ch5: IPU from (IPU -> EE)
         ch1: VIF1 (EE -> VU1)            ch6: SIF0 (IOP -> EE)
         ch7: SIF1 (EE -> IOP)            ch2: GIF (EE -> GS)
         ch8: SIF2 (EE <-> IOP)           ch3: fromIPU (EE -> IPU)
         ch9: SPR (from/to Scratchpad)    ch4: toIPU (IPU -> EE)
     - Supports three DMA transfer modes: Normal, Source Chain, and
       Destination Chain (parsing packet tags in memory without CPU intervention).

  5. Input/Output Processor (IOP):
     - MIPS R3000A 32-bit CPU running at 36.864 MHz with 2 MB of dedicated
       RAM.
     - Responsible for legacy PS1 backwards compatibility and controlling
       all console I/O peripherals: SIO2 (Gamepads, Memory Cards), USB 1.1
       (OHCI), SPU2 sound, CDVD optical drive, and DEV9 PCMCIA/Expansion bay.
     - Interfaces with the EE via the Subsystem Interface (SIF) across SIF0,
       SIF1, and SIF2 DMA channels.

  6. Sound Processing Unit 2 (SPU2):
     - Dual-core digital audio processor operating at 44.1 kHz with 2 MB
       dedicated sound buffer RAM.
     - 48 hardware voices supporting 4-bit ADPCM compressed audio, pitch
       modulation, noise generation, envelopes (ADSR), and hardware reverb.

2.2  The Two PS2 Pipeline Models (Rodrigo Copetti Architecture Analysis)

  Programming the PlayStation 2 effectively requires choosing an execution
  model that balances the heterogeneous coprocessors. As articulated in
  Rodrigo Copetti's PlayStation 2 Architecture study, the hardware supports
  two primary processing topologies: the Sequential Pipeline Model and the
  Parallel Pipeline Model.

  --------------------------------------------------------------------
  A. The Sequential Pipeline Model (Linear Chain)
  --------------------------------------------------------------------
  In the sequential pipeline, data flows synchronously through the hardware
  engines in a linear, assembly-line fashion:

    [EE Core] ----> [VU0 (Macro/Micro)] ----> [Main RDRAM]
                                                    |
                                                 (DMAC)
                                                    v
    [GS eDRAM] <--- (Path 1) <--- [VU1] <--- [VIF1 FIFO]

  Pipeline Progression:
  1. The EE Core executes application logic, physics collision, and scene
     traversal.
  2. The EE Core invokes VU0 (via COP2 macro instructions or VIF0 DMA) to
     perform matrix transformations, inverse kinematics, or skeletal bone
     animation.
  3. Transformed model coordinates are written back to main RDRAM.
  4. The DMAC (Channel 1) dispatches vertex data, normals, and texture
     coordinates through VIF1 into VU1 data memory.
  5. VU1 executes microcode to perform perspective projection, view-frustum
     clipping, lighting calculations, and screen-space conversion.
  6. VU1 streams formatted display packets directly into the Graphics
     Synthesizer via GIF Path 1.
  7. The GS rasterizes fragments into the eDRAM framebuffer.

  Characteristics:
  - Conceptually straightforward: Each processing stage has clear inputs
    and outputs.
  - Drawback: Downstream engines idle while upstream processors compute.
    The EE core frequently stalls awaiting memory writebacks or DMA completion,
    limiting overall throughput.

  --------------------------------------------------------------------
  B. The Parallel Pipeline Model (Decoupled Concurrent Nexus)
  --------------------------------------------------------------------
  In the parallel pipeline, the Emotion Engine and the Vector Units operate
  concurrently on different stages or independent rendering workloads:

    +-------------------+      (VIF1/VU1 DMA)     +-------------------+
    |      EE Core      | ----------------------> |    VU1 Engine     |
    |  - UI Compositor  |                         |  - 3D Mesh Trans. |
    |  - Window Manager |                         |  - Frustum Clip   |
    |  - SIF/HID Events |                         |  - Lighting Calc  |
    +-------------------+                         +-------------------+
              |                                             |
         (GIF Path 3)                                  (GIF Path 1)
              |                                             |
              v                                             v
    +-----------------------------------------------------------------+
    |                  Graphics Interface (GIF)                       |
    |        Arbiter multiplexes Path 1 (VU1) and Path 3 (EE)         |
    +-----------------------------------------------------------------+
                                    |
                                    v
    +-----------------------------------------------------------------+
    |                 Graphics Synthesizer (GS)                       |
    |         Parallel rasterization into 4 MB eDRAM at 48 GB/s       |
    +-----------------------------------------------------------------+

  Concurrency Mechanisms:
  1. VU1 Double-Buffering: VU1 data RAM (16 KB) is partitioned into two 8 KB
     buffers. While VU1 transforms and outputs vertices from Buffer 0 via
     GIF Path 1, VIF1 DMA unpacks the next mesh chunk into Buffer 1. When
     execution finishes, the buffers swap seamlessly without CPU stall.
  2. Simultaneous 2D/3D Rendering: While VU1 processes 3D scene geometry
     over Path 1, the EE Core composites 2D desktop windows, UI panels,
     and font glyphs, dispatching them over GIF Path 3 via DMA Channel 2.
  3. Autonomous VU0 Processing: VU0 operates in independent Micro Mode,
     executing physics simulations, particle updates, or math tasks in
     parallel with EE execution.
  4. GIF Arbitration: The hardware Graphics Interface arbitrates between
     Path 1 (VU1), Path 2 (VIF1), and Path 3 (EE Core) according to programmed
     priority, ensuring 2D UI composition and 3D geometry rendering do not
     interfere.

  The BTRON B-System adopts the Parallel Pipeline Model as its fundamental
  architecture. The EE core functions as the UI compositor and event
  coordinator, while VU1 and the GS execute graphics rendering asynchronously.


3. The plane table: periods and budgets belong to the machine
------------------------------------------------------------

  Execution time is partitioned across the four BTRON operating planes.
  Periods and cycle budgets are determined strictly by hardware silicon
  timings:

  Plane  Name             Target Engine    Period (us)   Budget (us)  Priority
  ----------------------------------------------------------------------------
  1      Input & HID      IOP/USB/Timer0          1000            50  Highest
  2      Media & Audio    SPU2/IOP SIF           20833          1500  High
  3      Window & 3D GS   EE / VU1 / GS          16666          4000  Standard
  4      Application      EE R5900          Cooperative     Variable  Lowest

  Plane 1 (1000 us, 50 us budget):
  - Driven by EE Timer 0 firing at 1 kHz.
  - Polls USB OHCI mouse/keyboard packets and DualShock 2 gamepad states
    via SIF RPC.
  - Updates mouse cursor coordinates and enqueues BTRON raw event records.

  Plane 2 (20,833 us, 1500 us budget):
  - Synchronized with 48 Hz audio buffering or optical disc streaming.
  - Dispatches ADPCM audio packets across SIF DMA to SPU2 sound RAM.

  Plane 3 (16,666 us for NTSC / 20,000 us for PAL, 4000 us budget):
  - Synchronized with GS vertical blanking (VSYNC interrupt).
  - The EE core traverses dirty window bounds, generates 2D drawing packets,
    and submits OpenGL ES / TinyGL display lists to the GIF DMA ring buffer.
  - Hardware rasterization occurs concurrently in GS eDRAM.

  Plane 4 (Cooperative timeslice):
  - Executes user-level BTRON applications: text editing, TAD documents,
    system settings, and shell utilities.

4. The Image Budget
-------------------

4.1  Memory Architecture and Physical Mapping

  The PlayStation 2 Emotion Engine provides 32 MB of Direct Rambus RDRAM
  operating on a dual-channel 16-bit 400 MHz bus (3.2 GB/s total bandwidth).
  The physical and virtual address space is mapped as follows:

  Segment  Virtual Range              Description
  ----------------------------------------------------------------------------
  KUSEG    0x00000000 - 0x7FFFFFFF    User Space (Cached)
  KSEG0    0x80000000 - 0x9FFFFFFF    Kernel Space (Cached via L1 Data Cache)
  KSEG1    0xA0000000 - 0xBFFFFFFF    Kernel Space (Uncached I/O & DMA buffers)
  SPRAM    0x70000000 - 0x70003FFF    Scratchpad RAM (16 KB, Fast Local SRAM)

  Physical Memory Allocation in BTRON B-System:
  0x00000000 - 0x000FFFFF (1 MB)    : EE Kernel Exception Vectors & Boot Stack
  0x00100000 - 0x004FFFFF (4 MB)    : BTRON B-System Core, Drivers, & Font Atlases
  0x00500000 - 0x006FFFFF (2 MB)    : Embedded /SYS Read-Only System Volume
  0x00700000 - 0x00FFFFFF (9 MB)    : GIF DMA Ring Buffers & Texture Caching Pool
  0x01000000 - 0x01FFFFFF (16 MB)   : Dynamic User Task Memory & Application Heap

  Memory Alignment Requirements:
  - DMA Buffers: Must be aligned to 128-bit (16-byte) boundaries.
  - Page Table & VRAM Transfers: Must be aligned to 64-byte cache line boundaries.
  - Scratchpad RAM Transfers: Must use 128-bit aligned quadwords.


5. One Calling Convention
-------------------------

5.1  MIPS R5900 ABI and 128-Bit Register Layout

  The BTRON PlayStation 2 core implements the MIPS 64-bit ABI extended for
  the R5900 128-bit multimedia architecture:

  Register   Mnemonic    Role / Preservation Convention
  ----------------------------------------------------------------------------
  $0         $zero       Always hardwired to zero (128-bit).
  $1         $at         Assembler temporary; clobbered by macro expansions.
  $2 - $3    $v0 - $v1   Function return values; caller-saved.
  $4 - $7    $a0 - $a3   Function arguments 0 to 3; caller-saved.
  $8 - $15   $t0 - $t7   Temporary registers; caller-saved.
  $16 - $23  $s0 - $s7   Saved registers; callee MUST preserve across calls.
  $24 - $25  $t8 - $t9   Temporary registers; caller-saved.
  $26 - $27  $k0 - $k1   Kernel exception handlers reserved.
  $28        $gp         Global pointer (points to small-data section).
  $29        $sp         Stack pointer; 16-byte aligned.
  $30        $fp / $s8   Frame pointer or saved register; callee-saved.
  $31        $ra         Return address; caller-saved.

  Quadword Assembly Instructions:
  - lq $rt, offset($base): Loads an entire 128-bit quadword into register $rt.
  - sq $rt, offset($base): Stores an entire 128-bit quadword to memory.
  These instructions allow 16 bytes of graphics or vertex data to be loaded
  or stored in a single clock cycle, providing optimal performance for
  GIF and DMA packet generation.


6. The FPU Law, and the register file inside it
-----------------------------------------------

6.1  Coprocessor 1 (FPU) Characteristics

  The Emotion Engine's COP1 floating-point unit adheres to the following
  hardware behavior:
  - Formats: Single-precision 32-bit floating-point numbers only. Double-
    precision (64-bit float) is NOT supported in hardware and generates
    software emulation traps.
  - IEEE 754 Conformance: Non-standard. Truncation is always toward zero
    (Round toward Zero mode).
  - Denormals: Denormalized numbers are NOT supported. Any denormalized
    operand is automatically flushed to zero (FTZ mode) without raising
    an exception.
  - Invariants: NaN values do not generate hardware signaling exceptions.

  LAW 6 (The Single-Precision Float Law).
  All operating system geometry, UI coordinates, and vector calculations
  shall use single-precision 32-bit floats (float) exclusively. Double-
  precision variables (double) are strictly forbidden in kernel and graphics
  paths.


7. One canvas, one byte order, one alpha
---------------------------------------

7.1  Canonical Pixel Format: PSMCT32

  The BTRON presentation engine standardizes on a single uncompressed color
  format: GS PSMCT32 (32-bit RGBA).

  Memory Byte Order (Little-Endian 32-Bit Word):
  Bits 00..07 : Red Component   (8 bits, 0x00 - 0xFF)
  Bits 08..15 : Green Component (8 bits, 0x00 - 0xFF)
  Bits 16..23 : Blue Component  (8 bits, 0x00 - 0xFF)
  Bits 24..31 : Alpha Component (8 bits, 0x00 - 0x80; 0x80 = 1.0 opaque)

7.2  GS Hardware Alpha Blending

  The Graphics Synthesizer computes alpha blending through the programmable
  formula configured in the ALPHA_1 register:

    Output = ((A - B) * C) >> 7 + D

  Where A, B, C, and D are selected from:
    A: 0 = Source Color (Cs),   1 = Dest Color (Cd), 2 = Zero
    B: 0 = Source Color (Cs),   1 = Dest Color (Cd), 2 = Zero
    C: 0 = Source Alpha (As),   1 = Dest Alpha (Ad), 2 = Fix Alpha (FIX)
    D: 0 = Source Color (Cs),   1 = Dest Color (Cd), 2 = Zero

  Standard Alpha Blending Configuration:
  - A = Cs (0), B = Cd (1), C = As (0), D = Cd (1)
  - Formula: (Cs - Cd) * As + Cd
  - Register encoding: GS_SET_ALPHA(0, 1, 0, 1, 0)

8. The measured microsecond
---------------------------

8.1  High-Resolution Hardware Timers

  Performance instrumentation on the PlayStation 2 relies upon two cycle-
  accurate hardware sources:
  1. CP0 Count Register: Increments every 2 CPU cycles (147.456 MHz).
     Resolution: 6.7816 nanoseconds per tick. Wraps every ~29.1 seconds.
  2. EE Timer 0 (0x10000000): Configured as a 16-bit countdown timer
     clocked at CPU/16 (18.432 MHz), providing 54.25 ns resolution for
     Plane 1 scheduling.


9. The instruments: which row answers which question
----------------------------------------------------

9.1  Telemetry Console and Metrics

  The BTRON kernel emits structured telemetry rows via the SIO serial port
  at 115200 baud to monitor frame health without disrupting graphics:

  Metric Token    Meaning
  ----------------------------------------------------------------------------
  frame=N         Monotonic frame sequence counter.
  us=T            Total frame elapsed duration in microseconds.
  ui=T            Plane 3 UI layout and window traversal duration.
  draw=T          Draw packet recording and vertex transformation duration.
  gif=T           GIF DMA dispatch and ring synchronization latency.
  verts=V         Number of vertices emitted to the GS in this frame.
  prims=P         Number of primitive drawing groups dispatched.
  drop=D          Refusal counter: packets dropped due to ring buffer fullness.


10. What a pixel costs
----------------------

10.1  Fill Rate Analysis and Bandwidth Limits

  The Graphics Synthesizer delivers a theoretical peak fill rate of:
    147.456 MHz * 16 pixels/cycle = 2.359 GPixels/sec (Untextured)
    147.456 MHz * 8 pixels/cycle  = 1.179 GPixels/sec (Textured)

  At 640x480 resolution (307,200 pixels per screen):
  - A full-screen clear costs: 307,200 / 16 = 19,200 GS cycles = 130.2 us.
  - A full-screen opaque 32-bit blit costs: ~260.4 us.
  - A 4x overdrawn UI composition costs: ~1041.6 us.

  Conclusion: The GS hardware rasterizer easily completes full-screen UI
  rendering well within the 4,000 us Plane 3 budget, provided that draw
  commands are batched and dispatched via GIF DMA rather than programmed I/O.

PART FOUR -- THE INTERCONNECT -- INPUT AS A REAL PLANE

12. The 1 kHz plane and the HID handover
----------------------------------------

12.1  IOP to EE Input Pipeline

  Human interface devices (USB keyboard, USB mouse, DualShock 2 controller)
  are managed physically by the IOP. Handover to the EE occurs through
  a structured SIF RPC ring:

    [USB Mouse] ---> [IOP OHCI Driver] ---> [SIF DMA Ring] ---> [EE Plane 1]
                                                                     |
                                                               (1 kHz Timer0)
                                                                     v
                                                            [Pointer Accumulator]
                                                                     |
                                                            [BTRON Event Queue]

  - The IOP polls USB endpoints every 1 ms and deposits 8-byte HID packets
    into an SIF ring buffer.
  - EE Timer 0 generates an interrupt every 1000 us, invoking Plane 1.
  - Plane 1 consumes all pending HID packets, updates mouse (X, Y) screen
    coordinates, and synthesizes BTRON pointer events (EV_BUTDWN, EV_BUTUP,
    EV_PTRMOV).


13. Which layer owns the pointer
--------------------------------

13.1  Hardware Cursor vs. Software Compositor

  In traditional software rendering, drawing a mouse cursor requires saving
  the framebuffer background, painting the cursor sprite, and restoring the
  background when the mouse moves. On the PS2, reading pixels from eDRAM back
  to EE memory over the bus is prohibitively expensive.

  The BTRON PS2 Core solves this through the Hardware Overlay Layer:
  - The mouse pointer is maintained as a dedicated 16x16 textured sprite
    stored in a reserved region of GS eDRAM (Page 63).
  - During the presentation pass, the compositor issues a single GIF sprite
    packet drawing the pointer at (cursor_x, cursor_y) as the very final
    operation before buffer display.
  - No framebuffer readback is ever performed. Pointer movement occurs with
    zero CPU blit overhead and sub-millisecond response latency.

PART FIVE -- THE PRESENTATION PLANE -- THE EE/GS BACKEND
=====================================================================

14. Why the Graphics Synthesizer, and only it
--------------------------------------------

  In early console ports, developers frequently treated video hardware as a
  simple linear framebuffer, using the CPU to render pixels into system RAM
  and blitting the finished canvas over the bus.

  On the PlayStation 2, this approach fails completely:
  - The EE core lacks sufficient cache and memory bandwidth to software-render
    640x480x32bpp at 60 frames per second.
  - Transferring a 1.2 MB framebuffer from EE RDRAM to GS eDRAM over GIF
    DMA consumes ~12 ms of bus time per frame.

  The BTRON PS2 core dictates that the Graphics Synthesizer is the SOLE
  rasterization engine. The EE core never touches frame pixels; it emits
  geometric drawing commands (GIF packets), and the GS rasterizes directly
  into eDRAM at 48 GB/s.


15. The standing laws of the present path
-----------------------------------------

15.1  The Presentation Invariants

  LAW 15.1 (Non-Blocking GIF DMA).
  The CPU shall never spin-wait on the GIF DMA channel status register
  (D2_CHCR & STR). All presentation packets shall be submitted to the
  asynchronous GIF Ring Buffer (ps2_gif_ring.c). Buffer recycling checks
  occur only at scheduler yield boundaries.

  LAW 15.2 (Minimal Register State Mutation).
  Drawing commands shall be sorted by primitive type and texture binding.
  Redundant updates to GS environment registers (FRAME, SCISSOR, TEST,
  ALPHA) within a single frame are strictly forbidden.

  LAW 15.3 (Single Execution Context).
  All standard 2D and 3D rendering shall target GS Context 1 (CTXT=0).
  Context 2 (CTXT=1) is reserved strictly for specialized destination-
  brightening blend passes.


16. The increments, and the lanes that follow
---------------------------------------------

16.1  Architectural Increments of the EE/GS Backend

  The presentation pipeline is constructed in six discrete architectural
  layers:

  Increment 1: Privileged GS Setup (ps2_gs.c)
  - Configures CRT timings (PMODE, SMODE2, DISP1, DISPLAY1).
  - Initializes video clocks for 640x480 NTSC interlaced or progressive mode.

  Increment 2: GIF Packet Encoder (ps2_gs_pack.c)
  - Generates 128-bit GIFTAG descriptors.
  - Supports PACKED format (RGBAQ + XYZ2), REGLIST format, and DIRECT mode.

  Increment 3: GIF DMA Ring Buffer (ps2_gif_ring.c)
  - Implements an asynchronous 64 KB double-buffered ring.
  - Provides lock-free submission from the EE core to DMA Channel 2.

  Increment 4: 2D Accelerated Primitives (ps2_gs_rec.c)
  - Implements hardware-accelerated solid rectangles, lines, and textured
    UI panels.
  - Maps BTRON window backgrounds and borders directly to GS primitives.

  Increment 5: Native OpenGL ES / TinyGL Backend (backend_eegs.c)
  - Implements a hardware-accelerated OpenGL ES subset.
  - Translates glBegin/glEnd, vertex arrays, texture uploads, and matrix
    transformations directly into GS GIF packets.

  Increment 6: Software TinyGL Rasterizer Adoption (backend_tinygl.c)
  - Fallback rasterizer for complex clipping and polygon algorithms that
    exceed GS hardware primitive limits.

18. The GS framebuffer architecture
-----------------------------------

18.1  4 MB eDRAM VRAM Memory Allocation

  The 4 MB eDRAM space is divided into 64 pages of 64 KB each (2048 words):

  VRAM Pages    Offset Range         Allocation Purpose
  ----------------------------------------------------------------------------
  00 - 09       0x000000 - 0x09FFFF  Front Framebuffer (640x480x32bpp, 600 KB)
  10 - 19       0x0A0000 - 0x13FFFF  Back Framebuffer  (640x480x32bpp, 600 KB)
  20 - 29       0x140000 - 0x1DFFFF  Z-Buffer Depth Buffer (32-bit Z, 600 KB)
  30 - 45       0x1E0000 - 0x2DFFFF  BTRON System Font Atlas (JIS + Tibetan)
  46 - 61       0x2E0000 - 0x3DFFFF  UI Icon Atlases and Application Textures
  62 - 62       0x3E0000 - 0x3EFFFF  Scratch Blit Page (Temporary Transfers)
  63 - 63       0x3F0000 - 0x3FFFFF  Hardware Mouse Pointer Sprite (16x16 RGBA)

  Buffer Stride and Base Addressing:
  - Framebuffer Width (FBW): 10 pages wide (10 * 64 = 640 pixels).
  - Front Buffer Base: Page 0 (FBP = 0).
  - Back Buffer Base: Page 10 (FBP = 10).
  - Z-Buffer Base: Page 20 (ZBP = 20).


19. Desktop, compositor, input mapping
--------------------------------------

19.1  BTRON Desktop on the PlayStation 2

  The BTRON desktop interface operates natively on the GS framebuffer:
  - The global system menu bar occupies the top 20 scanlines.
  - Windows are composited using hardware-accelerated GS textured rectangles.
  - DualShock 2 Input Mapping:
      D-Pad / Left Stick: Navigate focus / move pointer.
      Cross Button (X)  : Primary pointer click (Button 1).
      Circle Button (O) : Secondary pointer click / Context menu (Button 2).
      Square Button ([]) : Window resize / drag modifier.
      Triangle Button (/\\): Global Menu invocation.
      Start Button      : Open system workbench launcher.
      Select Button     : Cycle active windows.


20. The /SYS volume inside the executable
-----------------------------------------

20.1  Embedded Read-Only System Storage

  To ensure bare-metal bootability without requiring external hard disk or
  memory card configuration, the BTRON /SYS volume is compiled directly into
  the ELF binary:
  - Assembly Source: ps2_sys_vol.s
  - The file embeds a complete BTRON BFS file system image containing system
    fonts (JIS Level 1/2 Kanji, Tibetan Sambhota), default application
    configurations, desk accessories, and documentation.
  - At kernel startup, the VFS driver mounts the embedded volume as the root
    filesystem (/SYS), providing instantaneous file access without disc seek
    delays.

21. Build dials and their stamps
--------------------------------

21.1  Toolchain Configuration and Compiler Flags

  The PlayStation 2 target is compiled using the MIPS EE GCC cross-compiler:
  - Compiler: mips64r5900el-ps2-elf-gcc or ee-gcc.
  - Target Architecture: -march=r5900 -mabi=eabi -EL (Little-Endian).
  - Optimization Flags: -O2 -G0 -fno-common -mno-gpopt.
  - Float Flags: -mhard-float -mno-fused-madd.

  Makefile Invocation:
    make ps2          # Compiles the bare-metal ELF binary (btron-ps2.elf)
    make run-ps2      # Launches execution in PCSX2 emulator
    make test-ps2     # Executes automated regression test suite


22. Verification, and how a gate earns trust
--------------------------------------------

22.1  Automated Quality Gates

  The PlayStation 2 core is verified through a rigorous tiered test harness:
  - verify/tests/test_ps2_gs_rec.c: Validates GIF packet generation, NLOOP
    counters, and primitive vertex encoding without hardware dependency.
  - scripts/test_ps2.sh: Launches headless PCSX2, monitors console output
    via SIO, and verifies successful boot, filesystem mount, window manager
    initialization, and 60 Hz frame telemetry.
  - All automated gates must pass with 100% success before an image is
    deemed release-ready.


23. Running: PCSX2, MIPS, toolchain, quick reference
---------------------------------------------------

23.1  Deployment Instructions

  1. PCSX2 Emulation:
     Place btron-ps2.elf in the working directory and execute:
       pcsx2 -elf btron-ps2.elf -nogui

  2. Real Hardware Boot (FreeMCBoot / PS2Link):
     Transfer btron-ps2.elf via network using ps2client:
       ps2client -h 192.168.1.100 execee host:btron-ps2.elf

  3. Serial Debugging:
     Connect a 3.3V TTL-to-USB serial adapter to the PS2 mainboard UART port
     (Tx: Pin 12, Rx: Pin 10, GND: Pin 8). Open a terminal emulator at
     115200 baud, 8-N-1.


24. What is open, and what no measurement here can settle
---------------------------------------------------------

24.1  Architectural Frontiers

  While the BTRON PlayStation 2 core provides a robust, production-grade
  operating system environment, several advanced hardware capabilities
  remain open for exploration:
  - GScube Multi-Node Cluster Scaling: Utilizing the InterCore Nexus across
    multiple interconnected EE+GS nodes via high-speed SIF networks.
  - Microcode VU1 Geometry Streaming: Shifting dynamic lighting and vertex
    clipping entirely into VU1 micro-memory.
  - SPU2 Synthesizer Voice Expansion: Leveraging hardware DSP echo and chorus
    effects for the BTRON Lil Cu 64 sound synthesizer engine.

APPENDIX A -- LABEL SCHEME, DECODED
=====================================================================

  Register Definitions and Bitfields (ps2tek Reference):

  GS Privileged Registers (Mapped at 0x12000000):
  - PMODE (0x12000000)   : Power management, read/write circuits, CRT output.
  - SMODE2 (0x12000020)  : Interlaced/non-interlaced, NTSC/PAL video modes.
  - DISPFB1 (0x12000070) : Display buffer 1 base address, width, and format.
  - DISPLAY1 (0x12000080): Display buffer 1 screen position and dimensions.
  - CSR (0x12001000)     : System status, VBLANK interrupt flags, reset.

  GIFTAG Format (128-Bit Quadword):
  - Bits 00..15 : NLOOP  (Number of primitive loops / vertices).
  - Bits 16..45 : EOP    (End of Packet flag, bit 15 of high word).
  - Bits 46..57 : PRE    (Primitive output enable).
  - Bits 58..66 : PRIM   (Primitive type: Point, Line, Tri, Sprite).
  - Bits 67..70 : FLG    (Format: 0=PACKED, 1=REGLIST, 2=IMAGE).
  - Bits 71..74 : NREG   (Number of register descriptors in REGS list).
  - Bits 75..127: REGS   (List of target registers for packed data).

APPENDIX B -- MISALIGNMENTS WITH THE GOVERNING STANDARD
=====================================================================

  Conformity Notes with BTRON 3.20 Specification:

  1. Asymmetric Scheduling:
     The BTRON 3.20 specification originally assumed symmetric multiprocessors.
     The PS2 port resolves this by assigning dedicated Nexus agents to
     asymmetric hardware coprocessors (Law 1).

  2. Single-Precision Floating-Point:
     BTRON standard library math functions specifying 64-bit double precision
     are mapped to 32-bit single-precision float hardware on the R5900 core
     to avoid software trap overhead.

  3. eDRAM Coherence:
     GS eDRAM is not memory-mapped into the CPU address space. All pixel
     data must pass through the GIF DMA channel. Direct CPU framebuffer
     pointers are routed through the EE/GS presentation driver.
