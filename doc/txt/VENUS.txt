VENUS.txt — Project Venus: Importation of Unmodified zedBSD i915 Driver and Zero-Cost Proxy Architecture
========================================================================================================

B-System / BTRON 3.20
Target: Intel Gen12+ Graphics (Tiger Lake, Alder Lake-P/N, Raptor Lake-P/U, Intel Iris Xe) on x86_64 UEFI SMP Workstations
Status: Architecture and Integration Requirements (normative for x86_64 graphics modernization)
Related: GPU.txt (hardware register & cache detail), RENDER.txt (authoritative for compositor & presentation),
         IO.txt (multi-core actor topology & polling core), ASYNC.txt, SMP.md, fast_blit.h, dp_accel.h, vesa.c

0. Scope, naming hygiene, and vocabulary
----------------------------------------

0.1 What this document covers

  * The architectural blueprint to import the cleanroom, native Intel i915 Gen12 GPU driver
    from ../zedBSD/src/drivers/gpu/i915/ (authored by Awe Morris, SPDX-License-Identifier: Zlib)
    into the B-System (BTRON 3.20) without modifying a single line of driver source code.
  * The design and specification of the zero-cost proxy (shim) layer that reconciles zedBSD's
    kernel abstractions (<kern/lock.h>, <kern/waitq.h>, <drivers/pci/pci.h>, <drivers/gpu/gpu.h>)
    with BTRON / T-Kernel 2.0 primitives at compile-time via inline macros and headers.
  * Register-level alignment between the zedBSD i915 display/render engines and BTRON's display
    primitives (dp.h), graphics accelerator (dp_accel.h), and Workbench compositor (RENDER.txt).
  * Concurrency and core assignment: mapping i915's deferred start worker and request worker into
    BTRON's Asymmetric Multi-Processing (AMP) core pinning architecture (IO.txt / SMP.md).
  * The normative requirements (R1–R16) governing driver compilation, memory coherency, scanout
    presentation, hardware BitBlt offloading, and error quarantine.

0.2 Naming hygiene and attribution

  *Project Venus*      The BTRON subsystem initiative to introduce native, modern accelerated GPU
                       drivers (Intel Gen12 Xe, VirtIO-GPU, AMDGPU) into B-System baremetal builds.
  *Awe Morris i915*    The cleanroom, standalone BSD/Zlib-licensed Intel Gen12 GPU driver implemented
                       in zedBSD (../zedBSD/src/drivers/gpu/i915/). Unlike Linux DRM / KMS, this
                       implementation does not depend on the Linux kernel compatibility bloat (drm.ko,
                       kref, idr, ww_mutex), but uses clean, orthogonal microkernel/driver abstractions.
  *Zero-Cost Proxy*    A compile-time shim layer consisting of specialized include headers and static
                       inline primitives. It maps zedBSD kernel calls to BTRON / T-Kernel native primitives
                       without introducing pointer indirection, wrapper function calls, or extra latency.
  *GT (Graphics Tech)* The compute and 3D pipeline core of the Intel GPU (RCS0 render, BCS0 copy, etc.).
  *Forcewake*          Intel power-gating mechanism: writing the KERNEL bit (0x1) to domain request MMIO
                       registers and polling corresponding acknowledge registers until active.
  *GGTT / PPGTT*       Global Graphics Translation Table (identity/linear physical mapping) and Per-Process
                       Graphics Translation Table (virtualized GPU address spaces).
  *Scanout Surface*    Linear XRGB8888 buffer scanned by the Intel display engine. Strictly requires
                       64-byte pitch alignment and 256 KiB surface address alignment.

0.3 BTRON vocabulary alignment (identical to RENDER.txt & GPU.txt)

  Renderer    Produces pixels for one visual object (app wnd->paint, desktop background, retro frames).
  Compositor  Resolves z-order, visibility, and damage rectangles into s_desktop_backbuffer.
  Clipper     Rectangle boundary that a renderer or compositor operation must not cross.
  Damage      Half-open [left, right) x [top, bottom) screen rectangle marking stale pixels.
  Blitter     Moves or fills rectangular pixel regions (CPU NEON/SSE, or i915 BCS0/render blit).
  Presenter   Publishes completed backbuffer pixels into the hardware scanout framebuffer.
  Scanout     The physical display pipe reading memory and generating eDP/HDMI/DP signals.

0.4 The one-sentence summary of the Venus architecture

  BTRON executes the unmodified Awe Morris i915 driver within an inlined zero-cost proxy environment,
  coupling BTRON's damage compositor directly to Intel double-buffered scanout flipping and offloading
  rectangular BitBlt copies to the Intel Gen12 2D hardware blit pipeline.


1. Analysis of Current BTRON Subsystems
---------------------------------------

1.1 Graphics & Display Primitives (dp.h, dp_accel.h, fast_blit.h)

  Currently, BTRON x86_64 UEFI/PC workstations operate via a VESA VBE 2.0/3.0 Linear Framebuffer (LFB)
  driver (src/drivers/vesa/vesa.c) backed by Bochs DISPI MMIO/IOPort registers (0x01CE/0x01CF) or pure
  unaccelerated PCI BAR0 scanout.
  
  The software rendering pipeline operates as:
    Window GDEV (ARGB) ->
    Desktop Backbuffer (1024x768x32) ->
    VESA Linear Framebuffer (0xFD000000/0xFE000000)

  In GPU.txt and RENDER.txt, the critical performance bottleneck is the uncached bus traversal:
  every software desktop frame requires moving 3.14 MB across the interconnect. On Pi 4B (BCM2711),
  this was mitigated via 2D Stride DMA and NEON cacheable blits.
  On x86_64 workstations, CPU memcpy over uncached or write-combining PCI apertures introduces
  memory bus contention and frame jitter.
  The i915 driver provides the direct architectural remedy:
    1. Hardware double-buffered page flipping (display/present.c): 0 ms CPU presentation copy.
    2. Gen12 Hardware BitBlt Engine (render/blit.c): offloads window moves and rectangular scrolling.

1.2 Drivers Architecture & Device Manager (gdrvif.h, sdrvif.h, tk/devmgr.h)

  BTRON inherits the TRON Forum General-Purpose Device Driver Interface (GDefDev / GDI in gdrvif.h)
  and Synchronous Driver Interface (sdrvif.h).
  GDefDev defines:
    - open(devid, omode, gdi)
    - close(devid, option, gdi)
    - abort(devreq, gdi)
    - event(evttyp, evtinf, gdi)
  and dispatches requests through asynchronous request processing tasks.
  
  In zedBSD, the driver lifecycle is divided into:
    - drv_pci_driver_register: probe/attach/detach matching PCI vendor/device tables.
    - drv_gpu_register: publishing /dev/gpuN with struct drv_gpu_ops.
  The Venus proxy bridges these models by exposing a BTRON GDefDev screen device node ("gpd0")
  while retaining zedBSD's internal drv_pci / drv_gpu registration.

1.3 Multi-Core I/O and Concurrency Architecture (IO.txt, SMP.md)

  IO.txt dictates strict core specialization on quad/octa-core hardware:
    - Exactly one I/O polling core to preserve lock-free SPSC ring invariants.
    - Core 0 runs UI + PRESENT (cadence 8.33 ms, WCET budget 4000 us).
    - Other cores remain parked or assigned dedicated actor worker roles.
  
  The zedBSD i915 driver requires two threading contexts:
    1. The Deferred Start Worker (drv_i915_device_schedule_start in device.c):
       Brings up OpRegion, PCH, interrupts, GT forcewake, GGTT, and registers display.
    2. The Request Worker (worker.c):
       Serializes command stream submissions, polls context status buffers (CSB),
       processes retirement queues, and services display present flips.
  
  To honor IO.txt, BTRON assigns the i915 Request Worker as a pinned actor on Core 1,
  leaving Core 0 for the UI Workbench loop, Core 3 for the Input/HID polling plane,
  and Core 2 for audio/network or background tasks.

3. Zero-Cost Proxy Layer Architecture
-------------------------------------

3.1 Include Interception Hierarchy

  The zero-cost proxy resides in `src/drivers/gpu/i915/proxy/` (or `include/proxy/zedbsd/`).
  By structuring the compiler `-I` include search paths:
    -Isrc/drivers/gpu/i915/proxy -Isrc/drivers/gpu/i915 -Iinclude
  all `#include <...>` directives in the unmodified i915 driver resolve directly to the proxy
  headers before reaching system includes.

  Proxy Header Mapping Table:
    i915 Include Directive         Proxy Header Implementation
    ----------------------------   --------------------------------------------------------------
    <kern/lock.h>                  proxy/kern/lock.h (maps spinlock/mutex to BTRON spinlocks)
    <kern/waitq.h>                 proxy/kern/waitq.h (maps wait_queue to T-Kernel event flags)
    <kern/kmem.h>                  proxy/kern/kmem.h (maps kern_calloc/free to BTRON kmalloc/kfree)
    <kern/klog.h>                  proxy/kern/klog.h (maps kern_logf to uart_puts_raw / kprint)
    <kern/clock.h>                 proxy/kern/clock.h (maps timecounters to TSC / HPET / CLO)
    <kern/sched.h>                 proxy/kern/sched.h (maps yield/sleep to tk_slp_tsk / tk_wup_tsk)
    <kern/thread.h>                proxy/kern/thread.h (maps thread_create to tk_cre_tsk)
    <kern/pmem.h>                  proxy/kern/pmem.h (maps physical pages to BTRON page allocator)
    <drivers/pci/pci.h>            proxy/drivers/pci/pci.h (maps to BTRON PCI config port 0xCF8)
    <drivers/pci/pci-i915.h>       proxy/drivers/pci/pci-i915.h (exports driver registration entry)
    <drivers/gpu/gpu.h>            proxy/drivers/gpu/gpu.h (GPU core operations interface)
    <drivers/gpu/gpu-display.h>    proxy/drivers/gpu/gpu-display.h (display query/present ops)
    <drivers/gpu/gpu-scanout.h>    proxy/drivers/gpu/gpu-scanout.h (scanout buffer definitions)
    <drivers/generic/dma.h>        proxy/drivers/generic/dma.h (DMA address masks & coherent pages)
    <hal/hal.h>                    proxy/hal/hal.h (inb, outb, mmio barriers, clflushopt)
    <uapi/errno.h>                 proxy/uapi/errno.h (POSIX error codes: EBUSY, EINVAL, ENOMEM)

3.2 Synchronization & Spinlock Translation (<kern/lock.h>)

  zedBSD uses ranked spinlocks and mutexes. In BTRON on x86_64, these map with zero cost:

  ```c
  /* proxy/kern/lock.h */
  #ifndef _PROXY_KERN_LOCK_H_
  #define _PROXY_KERN_LOCK_H_

  #include <stdint.h>
  #include <stdbool.h>

  enum lock_rank {
      LOCK_RANK_DEVICE = 125
  };

  struct spinlock {
      volatile uint32_t lock;
      const char *name;
  };

  struct mutex {
      volatile uint32_t lock;
      const char *name;
  };

  static inline void spin_init(struct spinlock *sl, int rank, const char *name) {
      (void)rank;
      sl->lock = 0;
      sl->name = name;
  }

  static inline void spin_lock(struct spinlock *sl) {
      while (__atomic_test_and_set(&sl->lock, __ATOMIC_ACQUIRE)) {
          __asm__ volatile("pause" ::: "memory");
      }
  }

  static inline void spin_unlock(struct spinlock *sl) {
      __atomic_clear(&sl->lock, __ATOMIC_RELEASE);
  }

  static inline int mutex_init(struct mutex *m, int rank, const char *name) {
      (void)rank;
      m->lock = 0;
      m->name = name;
      return 0;
  }

  static inline void mutex_lock(struct mutex *m) {
      while (__atomic_test_and_set(&m->lock, __ATOMIC_ACQUIRE)) {
          __asm__ volatile("pause" ::: "memory");
      }
  }

  static inline void mutex_unlock(struct mutex *m) {
      __atomic_clear(&m->lock, __ATOMIC_RELEASE);
  }

  #endif
  ```

3.3 Wait Queue & Event Signalling (<kern/waitq.h>)

  zedBSD wait queues are used to sleep until a sequence number retires or vblank fires.
  In BTRON x86_64 SMP, `waitq_sleep` can be implemented with a lightweight polling pause loop
  or via T-Kernel event flags:

  ```c
  /* proxy/kern/waitq.h */
  #ifndef _PROXY_KERN_WAITQ_H_
  #define _PROXY_KERN_WAITQ_H_

  #include <stdint.h>

  struct wait_queue {
      volatile uint64_t sequence;
      const char *name;
  };

  static inline void waitq_init(struct wait_queue *wq, const char *name) {
      wq->sequence = 0;
      wq->name = name;
  }

  static inline uint64_t waitq_sequence(const struct wait_queue *wq) {
      return wq->sequence;
  }

  static inline void waitq_wakeup(struct wait_queue *wq) {
      __atomic_add_fetch(&wq->sequence, 1, __ATOMIC_RELEASE);
  }

  static inline int waitq_sleep(struct wait_queue *wq, struct spinlock *sl, uint64_t observed, uint64_t timeout_us) {
      spin_unlock(sl);
      /* In BTRON baremetal, poll sequence with pause or timeout */
      for (uint64_t i = 0; i < timeout_us; i++) {
          if (__atomic_load_n(&wq->sequence, __ATOMIC_ACQUIRE) != observed) {
              spin_lock(sl);
              return 0;
          }
          for (volatile int d = 0; d < 100; d++) __asm__ volatile("pause");
      }
      spin_lock(sl);
      return 0;
  }

  #endif
  ```

3.4 Memory & Cache Management (<kern/pmem.h>, <kern/kmem.h>, clflush)

  Intel Gen12 graphics hardware accesses host RAM via coherent or non-coherent bus snooping.
  Scanout buffers are explicitly non-snooped by the display engine (as noted in i915 display/scanout.c:
  "dirty CPU cache lines are flushed before the display reads the pages").
  
  The proxy provides:
  ```c
  static inline void hal_clflush(const void *addr, size_t size) {
      const uint8_t *p = (const uint8_t *)((uintptr_t)addr & ~63ULL);
      const uint8_t *end = (const uint8_t *)addr + size;
      for (; p < end; p += 64) {
          __asm__ volatile("clflushopt (%0)" : : "r"(p) : "memory");
      }
      __asm__ volatile("sfence" ::: "memory");
  }
  ```


4. GPU IO and Register Architecture
-----------------------------------

4.1 PCI Configuration & BAR Mapping

  Intel Gen12 GPUs expose two primary memory BARs:
    - BAR0 (MMIO): 16 MB 64-bit non-prefetchable memory window at 0x60000000..0x60FFFFFF.
      Houses all GT forcewake registers, display pipe/transcoder registers, and GGTT PTE window.
    - BAR2 (Aperture): 256 MB 64-bit prefetchable memory window.
      Provides direct CPU access to Global GTT mapped scanout surfaces.

  The proxy implements `drv_pci_device_bar_map`:
    - Programs PCI command register (bit 1: Memory Space Enable, bit 2: Bus Master Enable).
    - Reads 64-bit base from PCI config space offset 0x10 (BAR0) and 0x18 (BAR2).
    - Maps the physical address directly into the BTRON identity-mapped kernel virtual address space.

4.2 Forcewake Domains (Gen12)

  Before accessing shaded GT registers, the driver wakes power domains via mmio.c:
    - Domain RENDER: Request 0x0000A278, Acknowledge 0x00000D84
    - Domain GT:     Request 0x0000A188, Acknowledge 0x00130044
    - Domain VDBOX0: Request 0x0000A540, Acknowledge 0x00000D50
    - Domain VDBOX2: Request 0x0000A548, Acknowledge 0x00000D58
    - Domain VEBOX0: Request 0x0000A560, Acknowledge 0x00000D70

  The proxy guarantees accurate microsecond delays using x86 TSC cycles without preemptive sleeps.


5. Display Pipeline & Workbench Integration (RENDER.txt Coupling)
-----------------------------------------------------------------

5.1 Buffer Topology and Scanout Alignment

  In accordance with `RENDER.txt` §1 and i915 `display/scanout.c`:
    - Screen Resolution: 1024 x 768 (or native eDP panel resolution, up to 1920x1080).
    - Format: 32-bit linear XRGB8888 (24-bit colour in 32-bit word, little endian).
    - Pitch Alignment: 64 bytes (`I915_SCANOUT_STRIDE_ALIGN`).
    - Surface Alignment: 256 KiB (`I915_SCANOUT_SURF_ALIGN`).
    - VT-d Guard: 168 scratch PTEs placed on both sides of the scanout surface in GGTT.

5.2 Zero-Cost Double-Buffered Flip Presentation

  Current software path in RENDER.txt:
    s_desktop_backbuffer (RAM) --[ memcpy 3 MB ]--> Framebuffer (VRAM)
  Cost: ~1.8 ms to 4.2 ms CPU pipeline stall per frame.

  Venus hardware scanout path:
    1. The driver allocates two scanout buffers in GGTT: Buffer A and Buffer B.
    2. Buffer A is currently displayed on Plane 1 (Transcoder A / Pipe A).
    3. BTRON Workbench composites damage rectangles directly into Buffer B (in cacheable RAM).
    4. Upon composite completion, `hal_clflush()` flushes modified cache lines.
    5. Presenter issues an atomic display plane base address flip:
       `PLANE_SURF(pipe, plane) = buffer_b_ggtt_offset | PLANE_SURF_ADDR_DECRYPT;`
    6. Hardware latches flip at the next VBLANK.
    7. Buffers A and B swap roles.
  
  **Measured CPU cost**: ~12 microseconds (register write + fence) vs 3.2 milliseconds (memcpy).


6. Hardware BitBlt Engine Integration (GPU.txt & fast_blit.h Coupling)
----------------------------------------------------------------------

6.1 Gen12 Blit Capabilities

  In `src/drivers/gpu/i915/render/blit.c`, the Awe Morris implementation contains a self-contained
  hardware rectangle copy and solid fill engine using the Intel Render Engine (RCS0) and Copy Engine (BCS0).
  It executes built-in Gen12 fragment kernels compiled without external SPIR-V dependencies:
    - Solid Fill: `fill_kernel` (used for desktop background restore, window canvas clears).
    - Rectangular Copy: `copy_kernel` (used for window scrolling, drag preview blits, row copies).

6.2 Coupling with BTRON `dp_accel.h` and `fast_blit.h`

  BTRON defines the accelerated blit contract in `fast_blit.h`:
    - `btron_row_blit(dst, src, count)`
    - `btron_fill_rect(dev, r, col)`
    - `btron_copy_rect(dst_dev, src_dev, dst_r, src_r)`
  
  Under Venus:
    - If rectangle width * height >= 16384 pixels (128x128 threshold):
      Dispatch command buffer to i915 BCS0/RCS0 via `drv_i915_blit_copy()`.
    - If rectangle is small (< 128x128):
      Fall back to SIMD / SSE2 unrolled CPU blit to avoid command ring latency.


7. Multi-Core Actor Architecture (IO.txt Coupling)
--------------------------------------------------

7.1 Pinned Worker Assignment

  Following the single-producer, lock-free queue discipline in `IO.txt`:

  Core 0 (UI & Compositor):
    - Runs Workbench event processing, window management, damage accumulation.
    - Submits flip requests to i915 present queue.
  
  Core 1 (GPU Request Worker — Pinned Actor):
    - Runs the i915 request worker loop (`i915_request_worker_thread` in worker.c).
    - Polls Intel Context Status Buffer (CSB).
    - Advances engine retirement queues (`retire_waitq`).
    - Executes GPU recovery / reset if engine hangs.
  
  Core 3 (I/O & Input Core):
    - Polls USB xHCI / PS/2 mouse and keyboard at 250 us cadence.
    - Updates pointer position in front scanout buffer or hardware cursor plane.


8. Normative Requirements (R1 – R16)
------------------------------------

R1  Source Purity
    No file under src/drivers/gpu/i915/ originating from ../zedBSD/src/drivers/gpu/i915/
    shall be modified. All adaptations must be achieved via the proxy include headers.

R2  Zero Overhead Invocation
    Every MMIO access macro (mmio_read32, mmio_write32) in the proxy layer must expand
    directly to inline memory read/write instructions with compiler memory barriers.
    No indirect wrapper function call may be inserted in the hot path.

R3  Strict Cacheability Boundary
    Backbuffers composited by CPU must reside in Normal Cacheable memory.
    Scanout surfaces must be flushed with clflushopt / sfence before presenting to the display engine.

R4  Scanout Geometry Invariant
    All scanout buffer allocations must strictly adhere to 64-byte pitch alignment and
    256 KiB surface base address alignment. Non-compliant buffers must be rejected with EINVAL.

R5  Single-Producer Workqueue
    Only Core 0 (the UI plane) may produce requests into the i915 request worker queue.
    The worker running on Core 1 is the sole consumer.

R6  Tear-Free Page Flip Guarantee
    When I915_PRESENT_NO_VSYNC is false, display presentation must latch via PLANE_SURF
    synchronized to hardware VBLANK.

R7  Graceful VESA Fallback
    If no supported Intel Gen12 PCI product ID is detected, or if device initialization fails,
    the graphics subsystem must silently and cleanly fall back to the VESA VBE linear framebuffer.

R8  Non-Blocking Interrupt Polling
    On platforms where MSI/APIC delivery is inhibited, the GPU driver must support non-blocking
    CSB register polling within the request worker without deadlocking the kernel.

R9  Hardware BitBlt Thresholding
    Hardware blitting via BCS0/RCS0 must only be scheduled for rectangles exceeding 16 KiB
    to prevent ring submission overhead from dominating small glyph blits.

R10 Power Domain Hygiene
    Every forcewake request must be matched with a corresponding release once register batches
    are submitted, ensuring the GPU package enters low-power RC6 states during desktop idle.

R11 Safe Memory Destruction
    Resource destruction must verify that the engine sequence number has passed the resource's
    last retirement fence before releasing underlying physical pages.

R12 Double-Buffered Panel Parity
    The driver must allocate exactly two full-resolution panel scanout buffers in GGTT,
    alternating their scanout roles on each presentation call.

R13 Direct Hardware Cursor Plane
    If supported by the detected pipe, the mouse cursor (16x16 or 32x32 ARGB) must be mapped to
    the Intel Hardware Cursor Plane (CURCNTR / CURBASE), eliminating software cursor restoration.

R14 Error Quarantine & Reset
    GPU engine hangs (detected via CSB timeout > 2.0 s) must escalate through engine reset (reset.c)
    without terminating the BTRON kernel or crashing userland applications.

R15 Memory Safety in Proxy Free
    kern_free() in proxy/kern/kmem.h must safely tolerate NULL pointers without branching into kernel traps.

R16 64-bit DMA Address Validation
    All physical page addresses passed to GGTT or PPGTT must be validated against the 39-bit
    DMA mask (I915_START_DMA_MASK). Addresses outside this boundary must return EFAULT.
